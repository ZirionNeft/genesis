# Genesis: контекст для агентов

Этот файл применяется ко всему репозиторию. Информация об Hytale проверена
**13 октября 2026 года**. При обновлении игры сверяйте API и источники заново:
страницы документации и Maven-репозиторий меняются.

## Продукт и границы текущей работы

- Имя мода: **Genesis**.
- Разработчик: **Zirion**.
- Издатель: **if-else.dev**, сайт: https://if-else.dev.
- Целевая игра: **Hytale Release 0.7.0**, Update 7 / Chapter I.
- Текущая версия мода: `0.1.0-SNAPSHOT`.
- Реализованы загрузка серверного плагина и журналирование жизненного цикла;
  добавлен asset pack с мирным тестовым NPC `Genesis_TestNPC` для демонстрации моделей.
- Концепция описана в [Genesis_GDD_RU_v0.4.md](Genesis_GDD_RU_v0.4.md)
  от 14.10.2026. План реализации и состояние работ ведутся ниже в этом файле.
  Исходный GDD не изменяйте без прямого поручения пользователя. Различайте
  зафиксированные направления, предварительный баланс и открытые вопросы GDD.
  Не добавляйте игровые системы за его пределами, зависимости, способ хранения
  или лицензию без обоснованного решения для соответствующего этапа.

**Принятое техническое решение:** начать с Java server plugin в JAR.
Это соответствует существующему Java-проекту и программируемой серверной логике.
Asset pack уже включён в тот же мод. Генетическое ядро должно оставаться
независимым от Hytale; адаптер сервера и контент реализуются отдельно по
ответственности. Это не требует заранее вводить Gradle-мультимодульность.

## План реализации по GDD v0.4

План составлен **15.10.2026** по разделам 1–23 GDD. Он определяет порядок работ,
но не означает, что перечисленные механики уже реализованы. Текущая задача —
подготовка плана; реализацию этапов начинаем по дальнейшему поручению пользователя.
При уточнении дизайна обновляйте план и реестр решений здесь, сохраняя GDD.
Технические возможности Hytale проверяйте по артефакту целевой версии и клиенту;
примеры API, JSON и команд в GDD — проектные контракты, не готовый API игры.

### Как вести план

- Статусы: `TODO`, `IN_PROGRESS`, `BLOCKED`, `DONE`. У каждого этапа ниже есть
  зависимости и критерий готовности; выполненные задачи отмечайте `[x]`.
- При начале этапа обновляйте статус и ближайший шаг. При завершении записывайте
  дату, результат и подтверждение: тесты, пути к отчётам, серверная/клиентская
  проверка. Не отмечайте игровой этап готовым только по успешной компиляции.
- Блокировку описывайте конкретно: что неизвестно, какая проверка или решение
  её снимает. Независимые задачи можно продолжать, не выдавая допущение за факт.
- Решения с последствиями для сохранений, генетики и публичных форматов заносите
  в реестр ниже: выбранный вариант, причина, дата, затронутые этапы. Открытые
  вопросы не требуют повторного согласования уже разрешённых пользователем действий.
- Новые задачи привязывайте к этапу и разделу GDD. Уточнения пользователя имеют
  приоритет; расхождения фиксируйте здесь. Не расширяйте MVP поздними функциями.
- Подробные результаты длительных исследований можно хранить отдельными файлами;
  в плане оставляйте ссылку, принятое решение и оставшиеся ограничения.

### Объём и зависимости

**Играбельный MVP (GDD §21.1):** Клыкастые, волк и лисица, один гибридный
архетип; 12 независимых диплоидных локусов с небольшими полными таблицами
экспрессии; несколько полезных и вредных мутаций; приручение, короткая «Гармония»,
вольер, Искры и Колыбель, взросление, базовый спутник, Genesis Code, сохранения
и настраиваемый инбридинг. Для игрока должен работать весь цикл без отладочных
команд. Минимальная карточка, выбор пары и действия с Искрами входят в MVP;
полная лаборатория, рекомендации и регистрация пород — следующий этап.

До завершения MVP не включаем четыре полные группы, все хозяйственные линии,
уникальные магические анимации, рынок, межгрупповые гибриды, глобальные Хроники
и внешний сайт. Не вводим обязательную смерть от старости по умолчанию.

| --- | --- | --- | --- |

| 2B. Игровой вертикальный срез | TODO | 0, 1, 2A | Дикие волк/лисица → приручение → разведение → Искра → гибрид |

### Этап 0 — проверить анатомию и интеграцию NPC

Основание: GDD §§10, 18, 21. Зависимость: существующий тестовый NPC.

- [ ] Проверить API/ассеты 0.7.0 для замены головы, хвоста, текстуры и масштаба
  одного NPC; отдельно проверить пригодный четвероногий rig для Клыкастых.
  Демонстрационный гуманоид не считать готовым rig волка/лисицы.
- [ ] Проверить анимации, точки крепления, hitbox, опору, ориентацию и движение.
- [ ] Подтвердить видимость изменений второму клиенту, после повторного входа,
  выгрузки/загрузки сущности и перезапуска сервера.
- [ ] Проверить доступные взаимодействия и UI для будущего игрового цикла;
  не опираться на недоступный `dev_` Noesis UI.
- [ ] Сравнить модульную сборку с fallback: заранее подготовленные целые варианты
  тел + поддерживаемые attachments/текстуры. Зафиксировать фактические ограничения,
  контракт rig/слотов и выбранный путь, не изменяя генетические правила.

**Готово, когда:** есть воспроизводимый визуальный прототип на клиенте и запись
результатов по каждой проверке; основной путь либо fallback подтверждён в игре.
Независимые расчёты ядра можно готовить раньше, но контентный контракт не замораживать
до результата прототипа. Следующий шаг — этот этап.

### Этап 1 — независимое генетическое ядро

Основание: GDD §§2, 6, 8–12, 15, 18, 20. Зависимость: этап 0 для морфологии.

- [ ] Определить версионируемые реестры family/species/allele/ruleset и модель
  12 локусов: `FRAME`, `HEAD`, `LIMBS`, `APPENDAGE`, `PIGMENT`, `COVER`, `MUSCLE`,
  `STAMINA`, `METABOLISM`, `SENSE`, `TEMPER`, `ARCANA`. Для стартового набора
  заполнить все допустимые пары экспрессии и валидацию ссылок.
- [ ] Реализовать проверку группы/rig и отдельный расчёт успеха попытки:
  `clamp(C * R_A * R_B * E * Q, 0, 0.95)`. Несовместимую пару отклонять до
  расхода ресурсов; результат мини-игры не меняет передачу аллелей.
- [ ] Реализовать наследование по одному аллелю от каждого родителя, независимые
  локусы, канонический порядок сериализации, инъекцию RNG и версию его алгоритма.
  Генетический результат рассчитывать только после успешной попытки.
- [ ] Добавить не более одной de novo мутации на потомка, допустимые категории
  и локусы, явную политику пропуска недоступной мутации и обычное наследование
  уже существующих мутантных аллелей.
- [ ] Разделить генотип, морфологию, генетический потенциал и текущую эффективность.
  Сделать детерминированные resolver'ы, явные взаимодействия, пределы и цены
  преимуществ; максимум одну проявленную активную наследственную способность.
- [ ] Добавить происхождение, коэффициент родства и обработку частичной родословной;
  `developmentalFrailty` отделить от генов и от стандартных вероятностей наследования.
- [ ] Определить `GEN1` payload, checksum, schema/ruleset/asset-версии, косметический
  seed, режимы воспроизведения и политику миграций/отказов. UUID, владелец,
  обучение и provenance не входят в Genesis Code. Зафиксировать тестовые векторы.
- [ ] Добавить аналитические вероятности по независимым локусам и симулятор без
  создания NPC; проверить наследование, экспрессию, мутации, родство, codec и
  соответствие всех разрешённых генотипов поддерживаемой морфологии.

**Готово, когда:** ядро работает без игрового сервера, одинаковые входы/seed/версии
дают одинаковый результат, тестовые векторы воспроизводятся. Менделевские случаи
и родство из GDD §20.1 подтверждены; частотные проверки 100 000+ потомков имеют
фиксированный seed и статистически обоснованный допуск. Никаких перебросов генома
ради удобства визуализации.

### Этап 2A — состояние, конфигурация и надёжность

Основание: GDD §§7, 12, 15, 18–20. Зависимость: этап 1.

- [ ] По решению D02 выбрать способ хранения и представление Искры. Разделить
  геном, запись существа, `sparkId`, `breedingEventId`, владельца, происхождение,
  возраст, обучение и текущее состояние. Версионировать данные и настройки.
- [ ] Реализовать серверные настройки с валидацией, миграцией и сохранением
  связи старых геномов с ruleset. Вероятности ограничивать `[0,1]`; множители
  среды/мини-игры валидировать отдельно, поскольку они могут быть больше 1.
- [ ] Реализовать атомарную попытку: резервирование пары и места, расход,
  восстановление, фиксированный исход и создание одной Искры при успехе.
  Повтор того же события возвращает прежний результат; один родитель не может
  участвовать в двух одновременных попытках. Отказ до запуска не расходует попытку.
- [ ] Реализовать переходы хранения/рассеивания/воплощения без дублирования:
  одна Искра расходуется один раз, возврат ограничен обычными расходниками,
  воплощение создаёт новый UUID и сохраняет исходный геном/provenance.
- [ ] Обеспечить сохранение при выгрузке, переносе и перезапуске, восстановление
  незавершённых операций после сбоя и непротиворечивый результат при повторном
  запросе. Проверить права и владение на сервере.
- [ ] Реализовать `off/soft/strict`: `off` отключает дополнительную ослабленность
  независимо от вложенных настроек; изменения конфигурации не переписывают
  уже зафиксированные геномы и врождённые состояния.

**Готово, когда:** тесты повторов, конкурентных запросов, заполненной Колыбели
и сбоев не создают лишних Искр/существ или повторных списаний; после перезапуска
результат и происхождение сохранены. Диск и ожидание futures не блокируют tick мира.

### Этап 2B — полный игровой цикл Клыкастых

Основание: GDD §§3–7, 10, 13, 17, 21–22. Зависимости: 0, 1, 2A.

- [ ] Добавить волка, лисицу и гибридный архетип с согласованными моделями,
  анимациями, ролями NPC, стартовыми геномами и способом появления в мире.
- [ ] Реализовать наблюдение → контакт → привязанность: честные сигналы,
  `trust/fear` в `[0,100]`, реакцию на темперамент и частичное сохранение доверия
  после неудачи. Сохранять открытые сведения бестиария и владельца.
- [ ] Добавить минимальные вольер и Колыбель, согласованные рецепты/стоимость,
  выбор пары и объяснения отказа: возраст, доступность, группа/rig, родство,
  готовность, среда, материалы и место результата.
- [ ] Реализовать три раунда «Гармонии» с пошаговым режимом без таймера и
  отключением мини-игры настройкой сервера. UI показывает отдельно успех
  попытки и вероятность целевого генотипа, не обещая скрытых генов.
- [ ] Подключить Искры: сохранение, доступный уровню анализ, рассеивание,
  воплощение в детёныша. Не создавать NPC и AI-тики для хранимых Искр.
  Подтверждать необратимое рассеивание ценных/избранных образцов.
- [ ] Связать фенотип с внешностью и параметрами NPC, не подменяя неизвестные
  игроку сведения полным серверным геномом в UI или сетевых ответах.

**Готово, когда:** игрок проходит цикл от двух диких производителей до гибрида
через игровые взаимодействия; Искра не меняется от анализа и не перебрасывается
при воплощении. Подтверждены серверная загрузка контента и внешний вид на клиенте.

### Этап 2C — довести и принять MVP

Основание: GDD §§11–15, 17, 19–21. Зависимость: 2B.

- [ ] Реализовать детёныша → молодое → взрослое, базовое обучение и полезного
  спутника; определить минимальный набор команд из GDD §13.3. Проверить путь,
  возвращение домой и серверные лимиты активных животных.
- [ ] Добавить минимальную карточку животного, экспорт собственного Genesis Code
  и административное воспроизведение с проверкой прав, версий и входного кода.
  Обычный survival-импорт по умолчанию выключен; админ-спавн/импорт помечаются
  как не участвующие в первооткрытиях.
- [ ] Проверить совместную игру: конкуренцию за пару/Искру, разрыв соединения,
  повторный вход, выгрузку и перезапуск. Вне активной зоны не выполнять полный
  боевой AI-тик. Зафиксировать нагрузочный сценарий и измерения.
- [ ] Проверить en-US/ru-RU, клавиатуру, режим без таймера, читаемые сигналы
  помимо цвета, настройки эффектов и подтверждения необратимых действий.
- [ ] Провести плейтест темпа и полезности: первое приручение, первый гибрид,
  понимание вероятностей, стоимость содержания, причины выбора/рассеивания Искр.
  Оценивать медиану и высокий процентиль; не менять наследование ради защиты
  от невезения. Числа GDD пока являются ориентирами.
- [ ] Выполнить `clean build`/`verifyPluginJar`, содержательные тесты ядра и
  сохранений, запуск на 0.7.0 и клиентскую приёмку полного цикла. Обновить README
  по фактически доступным действиям; перечислить ограничения MVP.

**Готово, когда:** весь состав MVP работает после перезапуска и в мультиплеере,
гибрид полезен игроку, дюпы и критические проблемы цикла закрыты, а результаты
проверок записаны. Полный сценарий §22 проверяется в пределах возможностей MVP;
породы и Хроники принимаются на своих этапах.

### Этап 3 — целенаправленная селекция

Основание: GDD §§7, 12, 14, 17, 20. Зависимость: 2C.

- [ ] Развить бестиарий, лабораторию и уровни анализа: неизвестные гены показывать
  как неизвестные/интервалы. Добавить журнал целей и объяснимые рекомендации пар.
- [ ] Показать родословную, поколение, доли происхождения и риск родства;
  доли происхождения не дают дополнительных бонусов к характеристикам.
- [ ] Реализовать критерии стабильности и регистрацию пород, учёт оценённых
  потомков и производителей. Порода не меняет наследование; опциональный бонус
  относится только к успешности попытки.
- [ ] Открывать инструменты по прогрессии: ускоренное приручение изученного вида,
  автоматическое разведение освоенной группы, улучшение Колыбели и фильтры.
  Авто-режим не выгоднее правильно выполненной ручной мини-игры; фильтры видят
  только доступные игроку сведения. Проверить несколько вольеров и общую пару.
- [ ] Добавить дикие линии-носители как альтернативу массовому разведению;
  проверить стоимость циклов и отсутствие прибыли от рассеивания/повторных попыток.

**Готово, когда:** игрок может спланировать и закрепить целевую комбинацию,
понимает прогноз и риск, регистрирует породу по проверяемым критериям; автоматика
снижает рутину без раскрытия скрытого генома и изменения вероятностей аллелей.

### Этап 4 — роли, новые группы и баланс

Основание: GDD §§4, 9–11, 13–14, 20–21. Зависимость: 3.

- [ ] Расширять контент по одной группе: Бегуны, Тяжеловесы, Крылатые. Для каждой
  до включения проверить rig, все допустимые экспрессии, модули, анимации,
  коллизии, локализацию и воспроизводимость Genesis Code.
- [ ] Добавлять роли последовательными игровыми срезами: бой/защита, маунты,

- [ ] Подключить способности, снаряжение, физиологические расходы и влияние среды;

## Правила дальнейшей разработки

- Держите `GenesisPlugin` небольшим: регистрация интеграций в `setup()`, действия
  после старта в `start()`, освобождение собственных ресурсов в `shutdown()`.
  Используйте регистры плагина для команд, событий, ECS-компонентов и задач.
- Не храните игровую логику в конструкторе. Новые механики выделяйте в классы
  по предметной области после появления конкретных требований.
- Для логирования используйте `getLogger()`. Для пользовательского текста
  предусматривайте локализацию. Не заменяйте серверный API самодельными заглушками.
- Работу с миром и ECS выполняйте в предусмотренном API контексте потока мира;
  не блокируйте tick сетью, диском или ожиданием futures. Проверяйте контракт
  конкретного события: часть событий асинхронна.
- Для файлов мода используйте `getDataDirectory()`, а не абсолютные пути.
- Манифест попадает в **корень JAR**. Gradle подставляет `Version`, `ServerVersion`
  и `Main` при `processResources`; исходный JSON является шаблоном.
- `Authors` содержит Zirion; издатель отражён в описании, сайте и группе.
  Не добавляйте выдуманное поле `Publisher` без поддержки в актуальном codec.
- `ServerVersion` сейчас ограничен ровно `0.7.0`. Расширяйте совместимость только
  после проверки соответствующих сборок. Не используйте `*`, `latest` или `1.+`.
- `IncludesAssetPack` уже `true`, поскольку JAR содержит ресурсы тестового NPC.
  После изменения ресурсов проверяйте их загрузку на целевой версии игры.
- Не включайте HytaleServer, Assets.zip, credentials, логи и миры в Git или JAR.
  `run/` исключён из Git и находится вне каталога установки Launcher.
- Проверяйте сборку после изменения Java, Gradle или манифеста. Тестируйте
  содержательную бизнес-логику; загрузку и поведение в мире проверяйте отдельно
  на Hytale 0.7.0. Успешная компиляция сама по себе не подтверждает игровой запуск.

## Модели NPC: проверенные рекомендации

Проверено 13.10.2026 по [официальным рекомендациям арт-команды](https://hytale.com/news/2025/12/an-introduction-to-making-models-for-hytale),
[Hytale Models](https://github.com/JannisX11/blockbench-plugins/blob/master/plugins/hytale_plugin/about.md),
[ModelAsset Release 0.7.0](https://docs.hytale.com/assets/models/), установленному
плагину Hytale Models 0.11.0 и оригинальным ассетам 0.7.0. Художественные
рекомендации не следует считать обязательными ограничениями codec.

- Для NPC выбирайте `hytale_character`. Формат персонажа использует
  **64 единицы Blockbench / пикселя текстуры на метр**, prop/block — 32.
  Не исправляйте неверно выбранную плотность случайным масштабом в ModelAsset.
- Геометрия Hytale состоит из кубов и двусторонних плоскостей (quads).
  Для NPC выбирайте простой читаемый силуэт, крупные формы и стилизованные
  пропорции. Сферы, произвольные меши и сложная топология не соответствуют
  рабочему процессу официального плагина.
- Размеры PNG кратны 32 по обеим осям; квадратная текстура не обязательна.
  Используйте небольшой атлас, рисуйте мягкие тени и свет прямо в текстуре,
  избегайте шумных деталей, чисто чёрного и чисто белого. PBR-карты не являются
  стандартным способом создания Hytale NPC.
- Лимит модели — **255 экспортированных узлов**, а не 255 кубов.
  Каждый group становится node; первый подходящий не повёрнутый куб группы
  становится shape этого node, остальные кубы экспортируются отдельными nodes.
  Поэтому считайте результат codec, включая пустые группы, и проверяйте
  attachment-экспорты отдельно. У тестового NPC 13 nodes / 10 кубов / 120 треугольников.
- Соблюдайте UV-плотность Hytale: размеры UV-граней связаны с геометрией.
  Для изменения размера без изменения UV используйте native stretch;
  произвольное растягивание UV не поддерживается. Проверяйте все UV в пределах PNG.
- Группы задают иерархию и точки вращения. Имена узлов должны точно совпадать
  с целями `.blockyanim`; существующие анимации не подходят произвольному скелету.
  В модели тестового гуманоида: `Origin → Pelvis → Belly → Chest → Head`,
  ветви `R-Shoulder/R-Arm`, `L-Shoulder/L-Arm`, `R-Thigh/R-Foot`, `L-Thigh/L-Foot`.
  Это упрощённый скелет с собственной Idle-анимацией, не полный скелет Player.
- Position/Rotation группы влияют на дочерние узлы. Scale/Visibility/UV Offset
  в Hytale-анимации относятся к shape соответствующего узла. `.blockyanim`
  использует кадры с частотой 60 FPS; экспортируйте официальным плагином,
  который конвертирует секунды и вращения в формат движка.
- В установленном codec фронт — **+Z** (`south` в Blockbench), верх — +Y,
  основание персонажа ставьте на Y=0. Не принимайте вид камеры за ориентацию
  игрового NPC. Для персонажа проверяйте лицо, поворот, рост и опору ног в игре.
- `hytale_validate_model` MCP проверяет лишь число узлов основного экспорта
  и кратность размеров PNG. Дополнительно проверяйте UV, имена анимационных целей,
  shading, ссылки ресурсов и результат на клиенте; вызов валидатора не заменяет
  игровую проверку. У тестовой модели shading `standard`, непрозрачная PNG.

### Подключение NPC к игре

- В `Server/Models/Genesis/Genesis_<Name>.json` укажите `Model`, `Texture`,
  `EyeHeight`, `HitBox`, масштабы и необходимые `AnimationSets`.
  `Model`/`Texture` принимают пути относительно `Common/`, для NPC —
  `NPC/Genesis/<Name>/...`; анимации также задаются относительно `Common/`.
  JSON-ассет и `.blockymodel` — разные файлы с разными функциями.
- В `Server/NPC/Roles/Genesis/Genesis_<Name>.json` роль `Type: Generic`
  ссылается через `Appearance` на **ID ModelAsset**, а не путь к `.blockymodel`.
  Настройте движение, здоровье и `Instructions` под требования; для демонстрации
  тестовый NPC использует Walk-контроллер с гравитацией и BodyMotion Nothing.
  Он неуязвим, не атакует и не имеет конфигурации естественного спавна.
- Имена локализуйте: `NameTranslationKey: server.genesis.npcRoles.<ID>.name`
  соответствует строке `genesis.npcRoles.<ID>.name = ...`
  в `Server/Languages/<locale>/server.lang`. Добавлены en-US и ru-RU.
- Asset pack в JAR загружается через `IncludesAssetPack: true`; для этих
  JSON-ассетов отдельная Java-регистрация не нужна. `verifyPluginJar` проверяет
  упаковку и ссылки ресурсов демонстрационного NPC. NPC-role builder и клиент
  дополнительно проверяются при игровом запуске.
- Призыв из **чата подключённого игрока-оператора**:
  `/npc spawn Genesis_TestNPC`. Аргумент — ID роли. Команда требует игрока
  в мире; серверная консоль с одними координатами его не заменяет.
  Права выдаются из консоли `/op add <имя подключённого игрока>`.
  Синтаксис проверен по `NPCSpawnCommand` и `AbstractPlayerCommand` в JAR 0.7.0.
  Для справки `/npc spawn Genesis_TestNPC --help`; флаг `--facingRotation`
  поворачивает появляющегося NPC к игроку.

Проверка демонстрационного NPC 13.10.2026: `clean build` / `verifyPluginJar`
успешны; сервер загрузил Genesis asset pack и одну новую Generic-роль,
завершил NPC validation и восстановил авторизацию из encrypted storage.
Все 60 UV-граней укладываются в PNG и соответствуют размерам геометрии;
цели Idle-анимации существуют в экспортированной модели. Превью проверено
в Blockbench. Внешний вид, столкновения и анимация на игровом клиенте
пока требуют ручной проверки; не считайте серверную загрузку её заменой.

## Важное из патчноута 0.7.0

Источник: [Modder-Facing Patch Notes — Update 7, 12.10.2026](https://hytale.com/news/2026/10/modder-facing-patch-notes-update-7).

- Блоки читаются через секции `ChunkStore`; запись — `BlockOperations`.
  Старые accessor-интерфейсы и методы `WorldChunk.setBlock/breakBlock` удалены.
  Не ограничивайте высоту диапазоном 0–320.
- `TickProcedure.onTick` получает `CommandBuffer<ChunkStore>` и `Ref<ChunkStore>`;
  `TargetUtil` работает с `ChunkStore`.
- ECS поддерживает иерархии; системы по умолчанию обрабатывают корни.
- `DrainPlayerFromWorldEvent` асинхронный; конечный setter — `setDestinationWorld`.
  Сохранение universe resources имеет стадию `FLUSH_UNIVERSE_RESOURCES`.
- Часть флагов `ClientFeature` перенесена в `GameplayConfig`.
  Для заголовков используйте `EventTitleStyle` вместо `IsMajor`.
- Серверный Noesis UI с префиксом `dev_` ещё недоступен для использования.
- Изменились пакеты: клиент и сервер требуют совпадающей сборки протокола.
- WorldGen V2 получил `ContextPrecision`; у `GradientWarp` удалены `2D/YFor2D`.
  Encounter-ассеты требуют `Class`; способности используют `AbilityKeyword`.
- `BlockSection` имеет формат 7: открытый новым сервером мир нельзя вернуть
  старой версии без резервной копии.

Игровой контекст: [Chapter I — полный changelog, 12.10.2026](https://hytale.com/news/2026/10/chapter-i-out-of-the-breach)
добавляет Goblin Breach, подземелье, Runestones, ману, гаджеты и мини-игры;
моды также могут содержать целые миры. Это возможности базовой игры,
а не утверждённый функционал Genesis.
