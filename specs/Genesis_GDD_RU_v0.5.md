## 1. Видение и принципы

**Genesis** — мод, в котором игрок изучает поведение животных, приручает их, скрещивает совместимые виды, открывает мутации, создаёт наследственные линии и использует выведенных существ в приключениях, бою, путешествиях и хозяйстве.

Фокус не на бесконечном фарме случайных питомцев, а на **осмысленных решениях селекционера**. Скрещивание должно оставаться достаточно предсказуемым, чтобы игрок мог планировать результат, и достаточно вариативным, чтобы каждое новое сочетание было интересно.

### 1.1. Зафиксированные направления

- **Генетика умеренной сложности:** диплоидные локусы, скрытые аллели, доминантность, наследование, новые мутации; без обязательной симуляции хромосом и биологически точного мейоза.
- **Внешность модульная:** гибрид собирается из совместимых частей тела и визуальных модификаторов на поддерживаемом скелете.
- **Мир фэнтезийный:** допускаются межвидовые гибриды внутри игровых групп и магические признаки. Биологический реализм не должен блокировать интересный геймплей.
- **Нет главной единственной роли:** сопоставимая ценность боевых спутников, маунтов, вьючных, хозяйственных, разведывательных, поддерживающих и коллекционных животных.
- **Селекция без переполнения мира:** потомство сначала существует как «Искра жизни»; игрок сам решает, какое животное воплощать.
- **Серверная управляемость:** баланс, инбридинг, время восстановления и мини-игры настраиваются администратором.
- **Переносимый генетический код:** один и тот же Genesis Code при одинаковом наборе правил восстанавливает одинаковую наследственную сущность.
- **История происхождения:** породы, авторы, первые открытия и родословные фиксируются сервером.
- **Автономность и совместимость:** Genesis не требует других модов; не перехватывает чужих NPC и предоставляет необязательный версионируемый API расширений (ADR-001, раздел 24).

### 1.2. Дизайн-принципы

1. **Нет идеального универсального питомца:** увеличение одних возможностей требует затрат, ограничений или снижения других.
2. **Игрок влияет на результат знаниями, а не скрытыми «подкрутками»:** удачная мини-игра повышает шанс успешной попытки, но не меняет вероятности передачи конкретного аллеля.
3. **Каждое видимое изменение имеет причину:** цвет, силуэт, рога, броня и свечение соответствуют генетическим признакам или косметическим вариантам.
4. **Неприятные случайности объяснимы:** риск наследственных недостатков можно выяснить анализом генов и родословных.
5. **Повторение становится удобнее:** первый опыт ручной и исследовательский; освоенные действия можно автоматизировать.
6. **Генетика и визуализация разделены:** ограничения графического API не должны ломать генетический движок или сохранения.
7. **Мультиплеер авторитетен на сервере:** клиент не генерирует потомство, не назначает себе мутации и не регистрирует открытия.

### 1.3. Не-цели первой версии

Полная симуляция реальной генетики; произвольные межгрупповые гибриды; генерация новых скелетов на лету; бесконечное число активных боевых питомцев; глобальная кросс-серверная таблица авторства; гарантированное воспроизведение старых моделей без установленных ассетов.

## 2. Терминология и модель мира

| Термин | Значение |
|---|---|
| **Генетическая группа (`family`)** | Набор совместимых видов с общим анатомическим каркасом и допустимыми локусами. |
| **Вид (`species`)** | Исходное дикое животное: волк, лисица, конь и т. д. |
| **Гибридный архетип (`hybridArchetype`)** | Поддерживаемая модель сочетания видов в пределах группы. Это **не** автоматически новый биологический вид. |
| **Порода (`breed`)** | Зарегистрированная игроком стабильная селекционная линия с целевыми признаками. |
| **Геном (`genome`)** | Набор пар наследуемых аллелей. |
| **Локус (`locus`)** | Позиция гена, например `FRAME` или `ARCANA`. |
| **Аллель (`allele`)** | Вариант гена, например `normal`, `large`, `shadow`. |
| **Генотип (`genotype`)** | Конкретные пары аллелей особи. |
| **Фенотип (`phenotype`)** | Вычисленные проявленные признаки, характеристики и способности. |
| **Rig / скелет** | Система костей, анимаций, слотов и базовой геометрии. |
| **Искра жизни (`spark`)** | Сохранённый геном будущего существа до физического воплощения. Не NPC. |
| **Genesis Code** | Портативное кодирование полного генетического представления. |
| **`generationSeed`** | Seed расчёта конкретного скрещивания с фиксированными входами и алгоритмом RNG. |
| **`creatureId`** | UUID экземпляра; отличается у двух животных, созданных из одного кода. |
| **Открытие** | Запись о первом воплощении поддерживаемого архетипа или редкой формы на сервере. |

Разделяем четыре уровня:

```text
Genotype → Morphology → Phenotype → Role
(аллели)  (анатомия)  (свойства)   (назначение/обучение)
```

Роль не является наследуемым аллелем; её может изменить игрок в рамках физиологических возможностей питомца.

## 3. Основной игровой цикл

```text
Исследование биома
      ↓
Наблюдение и изучение повадок
      ↓
Приручение и получение производителей
      ↓
Селекционный вольер → подбор пары → подготовка среды
      ↓
Мини-игра «Гармония» / автоматический режим
      ↓
Успех → наследование → новая мутация (необязательно)
      ↓
Искра жизни → генетический анализ
      ├─→ сохранить в Колыбели
      ├─→ рассеять и частично вернуть обычные материалы
      └─→ воплотить → детёныш → взросление
                                 ↓
                     обучение / роль / хозяйство
                                 ↓
                регистрация породы / новый производитель
                                 ↺
```

**Главный игровой вопрос:** какой генетический результат выгодно сохранить ради текущих задач или дальнейшей селекции?

Игрок должен быстро получить первого полезного питомца. Многопоколенная оптимизация — дополнительная долгосрочная цель, а не обязательное условие прохождения обычного контента.

## 4. Группы, виды и функциональные классы

### 4.1. Генетические группы

Названия групп — **фэнтезийная игровая таксономия**, а не строгое соответствие реальным биологическим семействам.

| Группа | Стартовые виды | Общая анатомия | Профиль |
|---|---|---|---|
| **Клыкастые** | Лесной волк, лисица, каменный шакал | Средний четвероногий хищник | Бой, скрытность, поиск |
| **Бегуны** | Степной конь, лесной олень, песчаный рогач | Копытное четвероногое | Верховая езда, скорость, проходимость |
| **Тяжеловесы** | Мшистый зубр, горный кабан, пепельный бронебык | Массивное четвероногое | Груз, защита, производство |
| **Крылатые** | Теневой ворон, сумеречная сова, искрокрыл | Птица | Разведка, поддержка, компоненты |

Фантастические виды (например, искрокрыл, бронебык) и гибридные названия являются оригинальными концептами Genesis. При внедрении в Hytale необходимо согласовать их с контентом игры и ресурсными наборами мода.

### 4.2. Силуэты и передаваемые особенности

- **Волк:** мощные лапы, широкая грудь, шерстяной воротник; сила, чутьё, защитный темперамент.
- **Лисица:** узкая морда, крупные уши, пушистый хвост; ловкость, осторожность, скорость.
- **Каменный шакал:** костяные плечевые наросты, короткий покров; устойчивость, рывковая атака.
- **Конь:** длинные ноги, выраженная мускулатура, грива; седло, скорость, выносливость.
- **Олень:** стройное тело, ветвистые рога; манёвренность, прыжок.
- **Песчаный рогач:** спиральные рога, широкие копыта; жаростойкость, экономный бег.
- **Мшистый зубр:** массивный корпус, густая шерсть, растительные наросты; груз и шерсть.
- **Горный кабан:** низкое крепкое тело, клыки; таран, устойчивость к отбрасыванию.
- **Пепельный бронебык:** тяжёлая кожа, костяные пластины; броня и жаростойкость.
- **Ворон:** вытянутые крылья; дневная разведка и интеллект.
- **Сова:** широкие тихие крылья, крупные глаза; ночная разведка.
- **Искрокрыл:** медное оперение, светящийся хохолок; световые/электрические аномалии.

### 4.3. Примеры гибридов

| Название | Родители | Внешность | Польза | Компромисс |
|---|---|---|---|---|
| **Волколис** | Волк × лисица | Волчий корпус, лисьи уши и хвост | Быстрый охотник | Меньше брони |
| **Гриворог** | Конь × олень | Конское тело, ветвистые рога | Горный маунт | Невысокая грузоподъёмность |
| **Железноспин** | Зубр × бронебык | Тяжёлый корпус с костяными пластинами | Защита, груз | Низкая скорость |
| **Лунокрыл** | Ворон × сова | Тёмные перья, совиная голова | Ночная разведка | Хрупкость, слабый урон |

Гибрид — не обязательная фиксированная модель из двух родителей: набор модулей и цвет зависят от генотипа потомка. Примерные названия — игровые архетипы, а не отдельный генетический локус.

### 4.4. Функциональные классы

| Класс | Основная задача | Генетические/анатомические предпосылки |
|---|---|---|
| **Страж** | Защищать хозяина, перехватывать угрозы | HP, защита, боевые конечности |
| **Охотник** | Преследовать и наносить урон | Скорость, восприятие, способы атаки |
| **Скакун** | Перевозить игрока | Поддерживаемый rig, седло, допустимая нагрузка |
| **Носильщик** | Перевозить предметы | Грузовой rig, выносливость, сумки |
| **Разведчик** | Искать врагов и объекты | Восприятие, подвижность |
| **Производитель** | Производить шерсть, перья, яйца, особые материалы | Соответствующий биологический признак |
| **Поддержка** | Баффы, свет, лечение, предупреждение | Выраженные способности и подходящее поведение |

Животное может выполнять дополнительные простые функции, но выбирает **одну основную специализацию**. Право на маунта определяется анатомией, а не одной лишь высокой силой.

## 5. Приручение: изучение и доверие

### 5.1. Фантазия игрока

Не «накормил три раза — получил питомца», а «понял животное и заслужил доверие». При этом процесс должен ускоряться после открытия вида в бестиарии.

### 5.2. Три фазы

1. **Наблюдение.** Игрок изучает сигналы состояния, любимую пищу, страхи, отношение к дистанции и предметам.
2. **Контакт.** Короткая поведенческая мини-игра: на каждый сигнал выбрать логичное действие.
3. **Привязанность.** При достаточном доверии животное становится прирученным, принимает базовые команды и привязывается к владельцу.

Типичный первый контакт: 3–5 решений, общая целевая продолжительность первого приручения знакомого по сложности животного — около **3–7 минут** включая поиск и наблюдение (настройка балансом).

### 5.3. Состояние и действия

Сервер хранит шкалы `trust ∈ [0,100]` и `fear ∈ [0,100]`. Состояния поведения: *спокойствие, интерес, настороженность, страх, угроза*.

Примеры решений: предложить подходящий корм, отойти, замереть, дать понюхать предмет, использовать игрушку, прекратить контакт. Эффект зависит от `TEMPER`, состояния, обстановки и выбранного действия.

| Результат | Δ доверия | Δ тревоги |
|---|---:|---:|
| Очень удачно | +25 | −10 |
| Удачно | +15 | −5 |
| Нейтрально | +5 | 0 |
| Неудачно | −5 | +15 |
| Опасно | −15 | +30 |

Каждая шкала ограничивается `[0,100]`. При `trust = 100` и не критической тревоге — успешное приручение. При `fear = 100` животное убегает, а агрессивное может защищаться. Неудача **не стирает весь прогресс**: часть доверия сохраняется (ориентир 60%).

### 5.4. Темпераменты

| Темперамент | Особенности |
|---|---|
| Любопытный | Хорошо реагирует на новые предметы |
| Осторожный | Нуждается в дистанции и медленных действиях |
| Агрессивный | Сильнее реагирует на вторжение |
| Дружелюбный | Быстрее наращивает доверие |
| Пугливый | Выше штраф за ошибку |
| Независимый | Сложнее привязать, полезен для автономных задач |

Сигналы должны давать игроку честную информацию. Недопустимы необъяснимые ловушки, когда один и тот же контекст ведёт к противоположным результатам без визуальных признаков.

### 5.5. Различия по группам

- **Клыкастые:** дистанция, реакция на контакт и пищу.
- **Бегуны:** спокойное сближение и отсутствие резких движений.
- **Тяжеловесы:** безопасная территория, корм, снятие стресса.
- **Крылатые:** наблюдение, приманки, размещение предметов, привлечение на дистанции.

Первая встреча — полноценная мини-игра. После исследования вида в бестиарии доступно ускоренное приручение; сервер может отключать мини-игры целиком.

### 5.6. Доступность

Мини-игра не должна требовать высокой скорости нажатия или точного попадания курсором. Нужен пошаговый режим без таймера, читаемые сигналы, настройка анимаций и возможность переиграть контакт без длительного наказания.

## 6. Разведение: вольер и мини-игра резонанса

### 6.1. Предметы и сооружения

- **Селекционный вольер:** размещение подходящей пары, настройка среды и запуск попытки.
- **Колыбель Genesis:** хранение Искр жизни и воплощение выбранных геномов.
- **Лаборатория селекционера:** анализ скрытых генов и вероятностей.
- **Журнал Genesis:** цели селекции, родословные, открытия, список питомцев.

Для отдельных групп предусмотрены модификаторы вольера: лесной уголок, просторная площадка, защищённая зона, гнездовье. Это геймплейные условия, а не изменение правил передачи ДНК.

### 6.2. Условия запуска

1. Оба родителя взрослые, доступны и принадлежат поддерживаемым генетическим группам.
2. Разведение между группами запрещено в обычном режиме.
3. Оба родителя готовы, не имеют активного cooldown и не участвуют в другой попытке.
4. Требования к пище, среде и другим обычным ресурсам соблюдены.
5. У вольера/Колыбели есть место для результата.
6. Сервер разрешает разведение, пара не заблокирована политикой родства.

Один вид и зарегистрированная стабильная порода — базовая совместимость **0,90**; разные виды внутри группы — **0,70**; разные группы — **0**. Для гибридов без особых правил внутри одной группы используется 0,70.

### 6.3. Мини-игра «Гармония»

Три раунда, суммарно короткие (ориентир 30–60 секунд при первом знакомстве):

1. **Среда:** выбрать из предметов подходящий корм/укрытие/условие.
2. **Поведение:** определить удачный момент для сближения по состояниям обоих родителей.
3. **Резонанс:** синхронизировать два коротких визуальных ритма либо решить их пошаговый эквивалент.

Первые два раунда награждают за знания животного, третий — за освоение общей механики. Резонанс не редактирует аллели и не гарантирует редкую мутацию.

**Автоматизация:** после освоения группы доступно автоматическое разведение с умеренно меньшим бонусом к вероятности успеха. Полностью автоматический режим не должен быть выгоднее правильно выполненной ручной мини-игры.

### 6.4. Формула успешной попытки

\[
P_{success} = \operatorname{clamp}(C \cdot R_A \cdot R_B \cdot E \cdot Q,\ 0,\ 0.95)
\]

- `C`: 0,90 / 0,70 / 0 в зависимости от совместимости.
- `R_A`, `R_B`: готовность родителей в `[0,1]`.
- `E`: качество среды, начальный диапазон `[0,8; 1,1]`.
- `Q`: результат мини-игры, начальный диапазон `[0,9; 1,15]`.

Пример: `0,70 × 1 × 1 × 1,1 × 1,15 = 0,8855` → **88,55%**. При несовместимости разведение не запускается, а не просто выполняется с нулевым шансом.

**Неудачная попытка:** не создаёт Искру, расходует одну попытку и часть материалов, переводит пару на восстановление. **Удачная:** создаёт один генотип Искры. Генетическая случайность рассчитывается **только после подтверждённого успеха**.

### 6.5. Почему мини-игра не редактирует гены

Если родители оба `S/s`, вероятность `s/s` при успешном рождении всегда 25% (при отсутствии новой мутации), независимо от мастерства игрока. Успешность мини-игры повышает количество удачных попыток за тот же ресурс, а не даёт скрытый бонус к конкретному желаемому аллелю.

## 7. Искры жизни: селекция без армии лишних NPC

### 7.1. Проблема

При вероятности целевой комбинации 3,125% в среднем потребуется **32 успешных рождения**. Если каждое создаёт живого питомца, ферма быстро превращается в хранилище нежелательных NPC; вместе растут расходы памяти, требования к загонам и эмоционально неприятная необходимость избавляться от животных.

### 7.2. Решение: Искра жизни

После успешного скрещивания создаётся **Искра жизни** — запись с уже определённым геномом, потенциальной внешностью и метаданными происхождения. Она **ещё не является физическим животным**.

Игрок может:

- **Сохранить** Искру в Колыбели.
- **Проанализировать** доступные признаки.
- **Воплотить** Искру в детёныша с фиксированным геномом.
- **Рассеять** Искру и освободить место.

Рассеивание не считается гибелью питомца: живое существо ещё не возникло.

### 7.3. Экономика Искр

- Одна успешная попытка создаёт **одну** Искру.
- По умолчанию вместимость начальной Колыбели — **8**, улучшенной — **32**.
- Рассеивание **не** возвращает готовность родителей и не позволяет повторно бросить тот же результат.
- Возврат — максимум **25% обычных расходуемых материалов**, без возврата редких катализаторов и времени.
- Не допускается экономическая петля, в которой рассеивание и повторное разведение создают ресурсы.
- Искры можно держать как записи данных, без сущности, тиков ИИ, потребления еды или анимаций.

### 7.4. Уровни генетического анализа Искры

| Уровень игрока | Доступная информация |
|---|---|
| Начальный | Группа, предполагаемый силуэт, проявленные заметные признаки |
| Селекционер | Известные генетические маркеры, диапазоны характеристик, очевидные недостатки |
| Генетик | Полный геном, рецессивные аллели, точный генетический потенциал |

Анализ **никогда не меняет** Искру. Если сведения неполны, следует показывать «неизвестно» или интервал, а не выдумывать точность.

### 7.5. Автоматические фильтры

В поздней игре игрок может сохранять Искры с нужными признаками и автоматически рассеивать прочие. Фильтры опираются **только на сведения, доступные текущему уровню анализа**; иначе это бесплатный скрытый секвенатор.

### 7.6. Воплощение и судьба живых животных

Воплощённое животное проходит стадии роста; его можно оставить в коллекции, обучить, использовать в хозяйстве, передать другому игроку, оставить производителем или отпустить в мир. Массовая селекция не должна требовать воплощения каждого неудачного генотипа.

## 8. Геном и правила наследования

### 8.1. Формальная модель

В MVP используем **12 независимых диплоидных локусов**. Каждый локус хранит упорядоченную для сериализации пару аллелей, логически полученных по одному от каждого родителя. Для простых расчётов порядок пары при экспрессии не важен; при необходимости происхождение сохраняется отдельно.

\[
G = \{(a_1,b_1), (a_2,b_2), \ldots, (a_{12},b_{12})\}
\]

| Локус | Категория | Основное назначение |
|---|---|---|
| `FRAME` | Морфология | Размер, масса, корпус |
| `HEAD` | Морфология | Морда, голова, уши |
| `LIMBS` | Морфология | Конечности, походка, прыжок |
| `APPENDAGE` | Морфология | Хвост, рога, наросты |
| `PIGMENT` | Внешность | Цвет, рисунок |
| `COVER` | Внешность | Шерсть, перья, кожа |
| `MUSCLE` | Физиология | Урон, груз, потребление ресурсов |
| `STAMINA` | Физиология | Выносливость, восстановление |
| `METABOLISM` | Физиология | Корм, рост, регенеративные затраты |
| `SENSE` | Восприятие | Зрение, слух, обоняние |
| `TEMPER` | Поведение | Доверие, реакции, обучаемость |
| `ARCANA` | Магия | Одна проявленная активная наследственная способность |

Локус может иметь больше двух **возможных аллелей в популяции**, но каждое животное хранит ровно два на локус. Число локусов расширяется по версиям схемы.

### 8.2. Наследование

Для локуса `A/a` родитель передаёт `A` или `a` с вероятностью 50%. Для `A/A` передаёт `A` с вероятностью 100%. Локусы MVP независимы: хромосомное сцепление и кроссинговер не моделируются.

Пример `S/s × S/s`:

|  | S | s |
|---|---|---|
| **S** | `S/S` — 25% | `S/s` — 25% |
| **s** | `s/S` — 25% | `s/s` — 25% |

Если `S` доминантен, `s/s` проявляется в 25% рождений, а носители `S/s` — в 50%.

### 8.3. Экспрессия аллелей

Для каждого локуса поддерживаются:

1. **Полное доминирование:** одна копия подавляет рецессивный признак.
2. **Неполное доминирование:** гетерозигота даёт промежуточный фенотип.
3. **Аддитивность:** аллели складывают умеренные вклады.

Для многовариантных локусов пары разрешаются таблицами `expressions`, а не одним глобальным «уровнем доминантности». Все разрешённые комбинации должны иметь определённый результат.

Пример `FRAME`:

| Пара | Проявление |
|---|---|
| `normal/normal` | Обычное тело |
| `normal/large` | Крупное тело |
| `large/large` | Очень крупное тело |
| `small/large` | Среднее тело |
| `small/small` | Малое тело |

### 8.4. Комбинирование вероятностей

Для независимых целевых признаков:

\[
P(\text{все признаки}) = \prod_i P_i
\]

Если требуются 3 признака с вероятностями `0,50`, `0,25`, `0,25`:

\[
P = 0.50 \cdot 0.25 \cdot 0.25 = 0.03125 = 3.125\%
\]

Вероятность получить хотя бы один подходящий генотип за `n` **успешных** скрещиваний:

\[
P_{\ge1} = 1-(1-P)^n
\]

При `P = 0,03125` и `n = 32` вероятность около **63,8%**, а не 100%. Среднее количество успешных рождений до первого успеха — `1/P = 32`. Неудачные попытки разведения считаются отдельно.

### 8.5. Совместимость

| Пара | Уровень | Базовый шанс успеха |
|---|---|---:|
| Один исходный вид | A | 90% |
| Разные виды одной группы | B | 70% |
| Совместимые гибриды одной группы | B (по умолчанию) | 70% |
| Одна зарегистрированная стабильная порода | A (опциональное правило) | 90% |
| Разные группы | X | Запрещено |

Одинаковая порода даёт только бонус к вероятности **успешной попытки**, но **не меняет вероятности наследования аллелей**. В конфигурации можно отключить и этот бонус.

Необходима отдельная проверка `rigCompatibility`: генетическая группа должна иметь поддерживаемые анатомические выходы. Межгрупповые магические гибриды — будущие вручную заданные архетипы, не универсальное комбинирование всего со всем.

### 8.6. Последовательность расчёта

```text
validateParents()
validateFamilyAndRig()
validateBreedingRules()
rollBreedingSuccess()

for each locus:
    alleleA = drawOne(parentA[locus])
    alleleB = drawOne(parentB[locus])
    child[locus] = canonicalPair(alleleA, alleleB)

rollDeNovoMutation()
if mutation:
    selectCompatibleCategoryAndLocus()
    changeOneAllele()

validateGenomeAgainstRuleset()
resolveMorphology()
resolvePhenotype()
calculateAncestryAndKinship()
createSparkRecord()
persistAtomically()
```

**Правило безопасности:** не перебрасывать наследованные аллели лишь потому, что внешний вид оказался неудобен. Совместимость вариантов определяется **до запуска разведения**, а фенотип должен иметь детерминированное отображение или заранее определённый допустимый fallback, не изменяющий генотип.

## 9. Мутации, редкие признаки и слабости

### 9.1. Новые (de novo) мутации

Начальное распределение **на одно успешно созданное потомство**:

| Результат | Вероятность |
|---|---:|
| Нет новой мутации | **92,0%** |
| Косметическая | **4,0%** |
| Физиологическая | **2,5%** |
| Поведенческая/сенсорная | **1,0%** |
| Аномальная (магическая) | **0,5%** |

Общая вероятность новой мутации — **8%**. Для MVP не более **одной новой мутации за одно рождение**. Уже имеющиеся мутации не ограничены этим правилом: они наследуются как обычные аллели.

Алгоритм выбирает категорию, допустимый локус, новый аллель и заменяет одну из унаследованных копий. Если категория/аллель для этого сочетания недоступны, действует явно заданная политика пропуска, без незаметной замены целого генома.

### 9.2. Польза и цена

Ориентир для не-косметических новых мутаций: 30% преимущественно полезных, 40% полезных с существенной ценой, 30% преимущественно вредных. Это **веса генератора**, а не универсальная оценка полезности.

| Мутация | Польза | Цена / недостаток |
|---|---|---|
| Гипертрофия | +15–20% физического урона | Ниже скорость, выше аппетит |
| Защитные пластины | +18–25% защиты | Дополнительная масса, медлительность |
| Лёгкий скелет | Скорость и прыжок | Меньше HP, хрупкость |
| Развитые лёгкие | Больше выносливости | Ограничение пиковых силовых нагрузок |
| Регенерация | Восстановление HP вне боя | Значительный расход пищи/резерва |
| Ядовитые железы | Периодический урон | Слабее прямая атака |
| Тепловое зрение | Поиск скрытых целей | Ограничения обычного восприятия |
| Сияющая грива | Освещение | Невозможность полноценно скрываться |
| Плотный подшёрсток | Защита от холода | Перегрев в жаре |
| Ускоренный рост шерсти | Больше ресурсов | Выше расход корма |
| Усиленные сухожилия | Выше прыжок | Плата при тяжёлой нагрузке |

Некоторые аллели просто неблагоприятны:

| Аллель | Локус | Возможная экспрессия |
|---|---|---|
| `fragile_bones` | `LIMBS` | Меньше HP |
| `weak_joints` | `LIMBS` | Меньше грузоподъёмность |
| `unstable_metabolism` | `METABOLISM` | Сильно больше расход корма |
| `poor_vision` | `SENSE` | Хуже обнаружение |
| `nervous` | `TEMPER` | Срыв команды под стрессом |
| `weak_wings` | `LIMBS` (птичий набор) | Меньше времени полёта |

Эффект может быть рецессивным, доминантным или промежуточным; это определяется правилами конкретного аллеля.

### 9.3. Магические признаки

Локус `ARCANA` поддерживает: `dormant`, `shadow_affinity`, `regeneration`, `spark_affinity`, `toxin_affinity` и будущие варианты.

**Максимум одна проявленная наследственная активная магическая способность** (первоначальное правило). Если аллелей две разных разновидности, таблица экспрессии определяет единственный итог и возможные скрытые носительства. Пассивные эффекты из других локусов допускаются, но ограничены балансом.

Примеры активных умений: теневой рывок, щит, электрический разряд, лечение, эхолокация. Их параметры определяются отдельными файлами способностей; ген включает доступность, но не бессрочную бесплатную силу.

### 9.4. Взаимодействие генов

| Сочетание | Итог |
|---|---|
| Большой корпус + развитые мышцы | Сильный таран при высоком расходе выносливости |
| Большой корпус + слабые суставы | Повышенные ограничения груза |
| Подшёрсток + холодостойкость | Хорошая эффективность в мороз |
| Подшёрсток + жара | Риск перегрева |
| Ночное зрение + тихие движения | Сильный ночной разведчик |
| Регенерация + быстрый обмен | Быстро лечится, дорого содержать |

Взаимодействия задаются **явно**. Не следует делать неограниченное умножение всех положительных бонусов.

### 9.5. Откуда брать редкие гены

Два пути: случайные новые мутации и **дикие линии-носители** из редких биомов. Нахождение новой популяции должно быть разумной альтернативой разведения огромного количества животных на месте.

## 10. Модульная анатомия и визуальная генерация

### 10.1. Цель

Два разных генотипа должны создавать визуально различимых животных: корпус, морда, уши, хвост, рога, шерсть, оперение, пластины, размер и окраска. При этом все варианты обязаны работать с анимациями и коллизиями.

### 10.2. Слои внешности

```text
rig (четвероногий хищник / копытное / тяжёлый / птица)
  ├── body module
  ├── head module
  ├── limb module set
  ├── appendage module(s): tail / horns / crest
  ├── cover layer: fur / feathers / hide
  ├── pigment + patterns
  ├── cosmetic / magical overlays
  └── equipment sockets: saddle / bags / harness
```

Для MVP лучше заранее создавать совместимые варианты модулей для одного rig, а не пытаться на лету морфить произвольную геометрию или генерировать новые кости.

### 10.3. Связь генов и визуальных модулей

| Локус | Аллель | Визуальная экспрессия |
|---|---|---|
| `FRAME` | `large` | Крупный корпус |
| `HEAD` | `fox` | Узкая морда и крупные уши |
| `LIMBS` | `runner` | Длинные стройные конечности |
| `APPENDAGE` | `bushy_tail` | Объёмный хвост |
| `PIGMENT` | `shadow` | Тёмный рисунок |
| `COVER` | `dense_fur` | Длинный мех |
| `ARCANA` | `spark_affinity` | Эффекты свечения при проявлении способности |

Ген определяет **семантический признак**. Отдельный Morphology Resolver выбирает из реестра разрешённую модель/текстуру/attachment. Неиспользуемый либо скрытый аллель не обязан менять внешний вид.

### 10.4. Контракт модуля

```json
{
  "moduleId": "fox_head_02",
  "slot": "head_socket",
  "allowedRigs": ["quadruped_medium"],
  "modelAsset": "genesis/heads/fox_02",
  "textureVariants": ["normal", "shadow", "albino"],
  "requiredTags": ["canid"],
  "providedTags": ["long_ears"],
  "animationProfile": "quadruped_medium_v1",
  "hitboxProfile": "head_medium"
}
```

Имена слотов и ассетов являются проектным API Genesis, **не утверждением о готовых именах Hytale**.

### 10.5. Инварианты внешности

- Только модуль из разрешённого слота и rig.
- Совместимые точки крепления и анимации.
- Коллизия и посадка на маунта соответствуют размеру.
- Нет гарантированного полёта просто от наличия визуальных крыльев.
- Любой допустимый генотип имеет стабильное визуальное представление.
- Одинаковый код + одинаковые ассеты + одинаковый ruleset дают одинаковый внешний вид.
- Физические и косметические вариации не должны менять серверную генетику.

### 10.6. Технический риск

**Критический риск проекта:** неизвестно, в какой мере конкретная версия Hytale позволяет динамически комбинировать части скелетной модели отдельного NPC без ограничений анимации и синхронизации. Первый технический прототип должен проверить смену головы/хвоста/текстуры/масштаба у одного NPC, сетевую видимость, сохранение и коллизию.

**Fallback:** подготовленные целые варианты базовых тел + динамические attachments/текстуры, при неизменной модели генома.

## 11. Фенотип, характеристики и баланс

### 11.1. Генетический потенциал

Для характеристики `k`:

\[
S_k = \operatorname{clamp}\left(B_k \cdot \left(1+\sum_i g_{i,k}+\sum_j I_{j,k}\right), L_k, U_k\right)
\]

- `B_k` — базовый профиль анатомического архетипа.
- `gᵢ,ₖ` — вклад **проявленных** генов.
- `Iⱼ,ₖ` — заранее описанные взаимодействия.
- `L_k`, `U_k` — ограничения данного архетипа/роли.

Текущая игровая эффективность:

\[
S_k^{actual} = S_k \cdot T_k \cdot H_k \cdot E_k
\]

`T_k` — тренировка, `H_k` — здоровье/усталость/сытость, `E_k` — среда. Эти множители **не наследуются**. Двойной учёт одной и той же мутации в генах и метаболизме запрещён.

### 11.2. Нормализованные характеристики

Здоровье, сила, защита, скорость, выносливость, ловкость, грузоподъёмность, восприятие, обучаемость, обмен веществ. Нормализация 0–100 используется в интерфейсе и симуляторе; реальные игровые величины HP, урона и скорости калибруются под Hytale.

Стартовые **относительные** диапазоны изменения от базового архетипа:

| Показатель | Нижняя граница | Верхняя граница |
|---|---:|---:|
| HP | 70% | 145% |
| Сила | 70% | 135% |
| Защита | 70% | 140% |
| Скорость | 75% | 130% |
| Выносливость | 70% | 150% |
| Груз | 60% | 155% |
| Восприятие | 70% | 145% |

Достижение одновременно всех максимумов должно быть невозможно из-за генетических компромиссов, несовместимостей и ограничений арканных способностей.

### 11.3. Предлагаемые стартовые профили (условная шкала)

| Вид | HP | Сила | Скорость | Груз | Восприятие |
|---|---:|---:|---:|---:|---:|
| Волк | 65 | 70 | 75 | 15 | 70 |
| Лисица | 35 | 40 | 90 | 5 | 95 |
| Конь | 70 | 35 | 80 | 70 | 50 |
| Олень | 55 | 30 | 90 | 35 | 75 |
| Зубр | 95 | 55 | 40 | 100 | 40 |
| Кабан | 85 | 75 | 55 | 65 | 35 |
| Ворон | 30 | 20 | 75 | 0 | 90 |
| Сова | 35 | 35 | 65 | 0 | 100 |

Для полёта и наземного движения используем разные фактические единицы и правила; числа выше — только для проектных сравнений.

### 11.4. Энергетическая цена

Три расчётных ресурса: **выносливость** (физическая работа), **метаболический резерв** (питание/восстановление), **арканный резерв** (магические умения). Они не являются новыми обязательными локусами.

Большая масса, броня, мышцы, регенерация и свечение повышают расходы или уменьшают другие возможности. Предпочтительны понятные компромиссы, а не случайное наказание.

Пример базового расчёта пищи:

\[
F = F_0(1+0.30\max(0,M-1)+0.20\max(0,P-1)+0.25A)
\]

`M` — относительная масса, `P` — относительная развитость мышц, `A` — нагрузка активных арканных процессов от 0 до 1. Дополнительные модификаторы конкретного генома применяются **без повторного учёта** того же эффекта.

### 11.5. Экология и среда

| Биом | Преимущества | Издержки |
|---|---|---|
| Снег | Густая шерсть, холодостойкость | Теплолюбивым животным хуже |
| Пустыня | Лёгкий корпус, экономный метаболизм | Перегрев у густошёрстных |
| Лес/пещеры | Ловкость, ночное зрение | Очень крупные маунты ограничены |
| Болото | Сыростойкость, малая масса | Тяжёлым трудно двигаться |
| Горы | Прыжок, прочные суставы | Большой груз затрудняет движение |

### 11.6. Геймплейные роли и ориентиры баланса

- **Боевые:** один атакующий питомец ориентировочно 20–40% устойчивого PvE DPS игрока соответствующего прогресса. У сильных приёмов cooldown и стоимость; PvP балансируется отдельно.
- **Маунты:** скорость, прыжок, груз, проходимость и защита конкурируют. Роль требует подходящего rig и точки седла.
- **Вьючные:** малые 6–10 слотов; средние 10–16; тяжёлые 16–24 (первоначальный вариант, затем — условная масса).
- **Разведка:** обнаружение врагов, следов, интересных объектов; слабый прямой урон.
- **Хозяйство:** циклы шерсти/перьев/яиц/фэнтезийных материалов с кормом и временем; генетический прирост производительности ориентировочно ограничить 30–40%.
- **Поддержка:** временные усиления, предупреждения, освещение, ограниченное лечение.

Загрузка вьючного:

\[
V_{loaded}=V_0 \cdot \left(1-0.35\max\left(0,\frac{q-0.5}{0.5}\right)\right),\quad q\in[0,1]
\]

До половины заполнения штрафа нет; при полной загрузке скорость около 65% обычной. В будущем `q` лучше основывать на массе, а не только слотах.

### 11.7. Ограничения армии

Начальное серверное правило: **два активных спутника** и **один используемый маунт**; остальные содержатся в питомнике. Не допускается прохождение всего контента пассивной армией из десятков боевых NPC.

## 12. Родословные, инбридинг и породы

### 12.1. Родословная

Каждая воплощённая особь хранит свой UUID, UUID родителей, поколение, исходные доли происхождения и ссылки на родословную. Для гибридных видов доля происхождения рассчитывается как среднее:

\[
A_{child}(s) = \frac{A_{parent1}(s)+A_{parent2}(s)}{2}
\]

Волк × лисица → 50/50; этот гибрид × волк → 75/25. **Проценты происхождения не добавляют характеристики сверх конкретных аллелей.**

### 12.2. Базовая вероятность проявления рецессивных генов

Скрещивание двух носителей вредного `a` даёт `a/a` с вероятностью 25% независимо от того, родственники они или нет. У родственников чаще совпадают общие наследственные аллели, поэтому полезно учитывать родословную, но не подменять генетику прямым штрафом.

### 12.3. Коэффициент инбридинга

\[
F_{child} = \phi(parentA,parentB)
\]

где `φ` — коэффициент родства по родословной.

| Родство родителей (при неродственных основателях) | F потомка |
|---|---:|
| Неродственные | 0% |
| Двоюродные брат/сестра | 6,25% |
| Единокровные брат/сестра | 12,5% |
| Родитель × потомок | 25% |
| Родные брат × сестра | 25% |

Можно ограничить точность известной родословной 4 поколениями для MVP и показывать «частичная родословная». Отсутствие записи об общем предке — не доказательство реальной неродственности.

### 12.4. Настраиваемая игровая ослабленность

Помимо реального наследования вводится **опциональный игровой эффект** `developmentalFrailty`, не передающийся как новый ген. Он усиливает риск для очень близких линий, если это включено на сервере.

\[
P_{frailty}=\min(P_{max},K\cdot\max(0,F-F_0))
\]

По умолчанию мягкого режима `F₀ = 0,0625`, `K = 0,2`, `Pmax = 0,15`. Для `F = 0,25` получаем **3,75%** дополнительного риска; если эффект сработал, например, −8% к HP **этого животного**, без передачи отдельного аллеля.

**Важное разделение:** настройка инбридинга включает/отключает этот дополнительный игровой штраф, но не меняет стандартные менделевские вероятности.

### 12.5. Режимы сервера

| Режим | Правило |
|---|---|
| `off` | Нет дополнительных штрафов или запретов; родословная может продолжать записываться |
| `soft` (по умолчанию) | Низкий настраиваемый дополнительный риск |
| `strict` | Увеличенный риск и опциональный запрет при высоком `F` |

Параметры независимо настраиваются администратором. Изменения настроек **не переписывают** уже зафиксированные геномы и врождённые состояния существ.

### 12.6. Регистрация пород

Порода — именованная селекционная линия, а не новое генетическое правило. Предлагаемые требования:

- минимум **3 поколения**;
- минимум **8 оценённых потомков**;
- проявление целевых признаков не менее чем у **75%** оценённых особей;
- отсутствие критических недостатков у зарегистрированных производителей.

Регистрация не делает гены доминантными и не повышает их шанс наследования. Она даёт название, запись в журнале, историю и коллекционную ценность. Администратор может корректировать критерии.

## 13. Рост, обучение, команды и специализации

### 13.1. Стадии жизни

| Стадия | Возможности |
|---|---|
| Детёныш | Уход, контакт, ранние проявления фенотипа |
| Молодое | Базовое обучение, ограниченные команды |
| Взрослое | Полная роль, разведение, снаряжение |
| Пожилое (опционально) | Ограничения активности, статус ветерана |

Обязательную смерть от старости **не вводить по умолчанию**. Реалистичный режим можно оставить опцией сервера.

### 13.2. Обучение

Тренировки улучшают исполнительность и эффективность в границах генетического потенциала, но **не изменяют геном** и не наследуются. Доверие влияет на надёжность команд, а не напрямую на урон.

### 13.3. Базовые команды

- `Follow` — следовать.
- `Guard` — охранять область.
- `Defend` — защищать хозяина.
- `Attack` — атаковать цель.
- `Search` — искать следы/ресурсы.
- `ReturnHome` — вернуться в назначенный питомник.
- Позднее: `Fetch`, `Distract`, `Carry`, маршруты и автономные задания.

### 13.4. Боевые роли

Страж/танк, охотник/ассасин, контроллер, поддержка. Система ИИ должна учитывать дистанцию, состояние, назначенный режим, угрозы и возможность найти путь. Сложная тактическая автономность — не требование MVP.

## 14. Экономика, прогрессия и антигринд

### 14.1. Четыре ступени прогрессии

1. **Новичок:** приручение, простые Искры, приблизительные признаки.
2. **Заводчик:** совместимость, журнал, расширение Колыбели.
3. **Селекционер:** родословные, рекомендации пар, автоматизация освоенных мини-игр.
4. **Генетик:** полный анализ генома, расширенные фильтры, параллельные вольеры, редкие линии.

Опыт открывает **инструменты**, а не глобальный бонус к получению нужных аллелей. Редкие гены можно искать в мире, а не только выбивать случайными попытками.

### 14.2. Борьба с рутиной

- Изученный вид проще приручать повторно.
- Освоенная группа допускает автоматическое разведение.
- Ненужные геномы не воплощаются, а рассеиваются.
- Селекционный журнал показывает цели и подходящие пары.
- Фильтрация Искр работает без ручного открытия каждой, но не раскрывает неизвестные гены бесплатно.
- Возможны параллельные вольеры, **одно животное не участвует в двух попытках одновременно**.
- Редкие признаки встречаются у диких популяций, стимулируя исследование биомов.

### 14.3. Целевые показатели темпа (только для плейтестов)

| Событие | Целевой темп |
|---|---|
| Первое приручение | ~3–7 минут |
| Первое гибридное потомство после получения пары | ~10–20 минут |
| Первый полезный редкий признак | ~30–60 минут активной игры |
| Сложная комбинация нескольких признаков | Несколько игровых сессий, не обязательный прогресс |

Важно отслеживать медиану и высокий процентиль ожидания: игрок с невезением не должен попадать в безнадёжную последовательность сотен обязательных попыток. Для обязательных сюжетных задач предпочтительнее гарантированный способ получить **функционально достаточного** питомца, а не гарантия редкого конкретного генотипа.

### 14.4. Экономика хозяйства

Ресурсы требуют времени, еды и пространства; специальные селекционные линии повышают эффективность ограниченно. Базовая формула производства:

\[
Y = Y_0 \cdot G \cdot N \cdot E
\]

`Y₀` — базовый выпуск за цикл; `G` — генетический модификатор; `N` — питание и здоровье; `E` — условия. Стартовый прирост производительности через генетику — не более примерно 30–40% относительно обычной линии до баланс-тестов.

### 14.5. Мультиплеер

Покупка, обмен, питомники и рынок пород — опциональные поздние функции. Торговля не должна переносить статус первооткрывателя, подменять provenance или раскрывать скрытый геном без согласия владельца, если сервер использует приватность генов.

## 15. Genesis Code и детерминированное воспроизведение

### 15.1. Три разных идентификатора

| Идентификатор | Назначение |
|---|---|
| **`genesisCode`** | Восстанавливает наследуемое содержимое и детерминированную косметику. У одинакового генотипа может быть одинаковый код. |
| **`generationSeed`** | Воспроизводит конкретную процедуру скрещивания только с известными входами, версией алгоритма RNG и родителями. |
| **`creatureId`** | Уникальный UUID каждого воплощённого экземпляра. |

Отдельный `breedingEventId` / `sparkId` обеспечивает уникальность происхождения. **Не нужно вставлять случайный `birthNonce` в сам генетический код**, если цель — получать идентичный код для генетически и косметически идентичных животных. Для паспорта конкретной особи существуют метаданные события.

### 15.2. Что воспроизводит код

- версию схемы генома;
- ID набора генетических правил и совместимых ассетов;
- генетическую группу и допустимый архетип;
- все пары аллелей, включая рецессивные;
- фиксированный косметический variant seed или ID вариантов;
- все наследуемые исходные параметры морфологии.

Код **не содержит** владельца, UUID экземпляра, текущих HP, еды, инвентаря, приобретённого обучения, статуса открытия или полной истории родословной.

### 15.3. Формат

```text
GEN1-<Base32(canonical_binary_payload)>-<checksum>
```

Пример **нерабочего сокращённого обозначения**, только для документации:

```text
GEN1-7KD4-V9MP-3TR6-...-CHK
```

Полный автономный код может занимать десятки или сотни символов, в зависимости от будущей схемы. Контрольная сумма обнаруживает ошибки копирования, **но не удостоверяет происхождение** и не является подписью.

### 15.4. Детерминированность

\[
Phenotype = Resolve(Genome, RulesetVersion)
\]

Одинаковый геном, ruleset и набор совместимых моделей должны давать одинаковый результат. Все дополнительные случайные косметические решения должны быть частью кода или детерминированно выводиться из включённого seed по зафиксированному алгоритму.

При обновлениях возможны два режима:

1. **Генетическое воспроизведение:** геном неизменен, фенотип пересчитывается по текущему ruleset.
2. **Точное воспроизведение:** требуется поддержка указанного ruleset и ассетов; если их нет — честная ошибка/предупреждение, а не незаметная подмена.

Нужны schema migrations, правила удаления/переименования аллелей и матрица совместимости версий.

### 15.5. Импорт и безопасность

- Экспорт собственного генома разрешён игроку при включённой настройке.
- Спавн по коду — по умолчанию **только администратору**; не даёт автоматических достижений и первооткрытий.
- Обычный импорт на публичном survival-сервере выключен.
- Код валидируется: длина, версия, checksum, неизвестные аллели, несовместимые rig, лимиты характеристик, доступность моделей.
- Если позднее нужна межсерверная доказуемая родословная, потребуется **отдельная криптографическая подпись сервера**, а не checksum.

Предлагаемые команды (не готовые команды Hytale):

```text
/genesis spawn <genesisCode>
/genesis inspect <creatureId>
/genesis export <creatureId>
/genesis breed --parentA <id> --parentB <id>
/genesis simulate --parentA <id> --parentB <id> --count 10000
```

`simulate` не создаёт существ и не расходует игровые попытки; для точных вероятностей 12 независимых локусов предпочтительнее аналитический расчёт, а симуляции нужны для проверки и сложных взаимодействий.

**Совместимость с другими модами:** при наличии внешних генов или анатомических модулей Genesis Code хранит namespaced ID, версии обязательных расширений и канонически сериализуемые данные. Если расширение отсутствует, генетические данные сохраняются, но импорт/спавн, требующий неизвестных правил, отклоняется без частичного результата. См. ADR-001, п. 24.7.

### 15.6. Внешний калькулятор

Будущий сайт сможет декодировать Genesis Code, показывать модель/характеристики, сравнивать родителей, рассчитывать наследование, выбирать оптимальную пару и делиться генетическими паспортами.

Для сайта генетическое ядро должно иметь **документированный формат и тестовые векторы**, чтобы реализации Java и TypeScript/WASM выдавали одинаковые результаты.

## 16. Хроники Genesis: история открытий

### 16.1. Не каждый геном — новый вид

Уникальные сочетания аллелей возникают часто. Поэтому три уровня открытий:

| Тип записи | Когда появляется |
|---|---|
| **Гибридный архетип** | Впервые воплощён поддерживаемый тип межвидового гибрида |
| **Редкая наследственная форма** | Впервые воплощена заранее определённая редкая комбинация |
| **Зарегистрированная порода** | Выполнены критерии стабильности и оформлена порода |

### 16.2. Авторство

- **Первооткрыватель:** первым воплотил новую форму/архетип на сервере согласно правилам мира.
- **Селекционер:** создал конкретную Искру.
- **Основатель породы:** зарегистрировал стабильную линию.
- **Владелец:** текущий хозяин конкретного животного.

История и первенство привязаны к стабильным UUID игроков, не к отображаемым именам.

### 16.3. Момент регистрации

Форма фиксируется при **первом физическом воплощении**, не при создании Искры. Автор Искры сохраняется в provenance. Если её воплощает другой игрок, правила отдельно различают селекционера и первооткрывателя.

Технически регистрация должна использовать атомарную уникальную запись по `(worldId, discoveryKey)`; при гонке только одно воплощение получает первенство.

### 16.4. Защита от злоупотреблений

Административно созданные животные и импортированные на сервер геномы **по умолчанию не участвуют в первооткрытиях**. Передача питомца не изменяет первоначальных заслуг. Часть генома редкого животного может оставаться приватной.

**Происхождение внешних данных:** админ-спавн и импорт геномов через расширения не создают первооткрытий по умолчанию. Авторство конкретного NPC и контроль над ним — отдельные сущности; интеграции не могут переписывать provenance чужой линии. См. ADR-001.

### 16.5. История линий

Сервер ведёт граф: предки, потомки, поколение, генетические изменения, приобретённые признаки, авторы важных событий, даты открытия пород. Позднее — публичная выставка коллекций и общий веб-каталог при явной политике межсерверного доверия.

## 17. Игровые интерфейсы и UX

### 17.1. Карточка животного

Показывает имя, гибридный архетип, породу, возраст, владельца, основную роль, нормализованные характеристики, выявленные достоинства/недостатки, команды и Genesis Code (при доступных правах).

### 17.2. Бестиарий

Изученные виды, корм, повадки, среда, вероятность нахождения редких диких линий, история первого контакта. До открытия часть информации скрыта.

### 17.3. Селекционный вольер

Выбор двух родителей, совместимость, причины отказа, готовность, условия, риск родства и кнопка «Начать гармонию». При неизвестных генах показывается прогноз **по имеющимся данным**, а не ложная точность.

### 17.4. Колыбель

Список Искр, фильтры, сравнение генетических профилей, подробный анализ, «Воплотить» или «Рассеять». Нужны подтверждения для необратимого рассеивания уникальных или избранных образцов.

### 17.5. Генетическая лаборатория

Геном по 12 локусам, известные и скрытые аллели, прогноз фенотипа, комбинации родителей, вероятность конкретной селекционной цели.

### 17.6. Журнал селекции

Возможность задать «желаемого питомца»: признаки, роль, минимальные характеристики, недопустимые недостатки. Система предлагает подходящие пары и объясняет результат.

### 17.7. Хроники

Открытия сервера, авторство, карта пород, граф родословной, выставка редких форм, история изменений линии.

### 17.8. UX-правила

- Различать **вероятность успешного разведения** и **вероятность нужного генотипа при успешном потомстве**.
- Не раскрывать скрытые аллели до соответствующего исследования.
- Всегда объяснять несовместимость и невозможность посадки/экипировки.
- Давать отмену/подтверждение для необратимых действий, особенно рассеивания ценных Искр.
- Мини-игры доступны без таймера и с настраиваемыми эффектами.
- Интерфейс не должен требовать постоянного переключения между десятками животных ради одной операции.

## 18. Техническая архитектура

### 18.1. Разделение ответственности

```text
Genesis Core (Java, independent of Hytale)
 ├── Family / Species / Allele Registries
 ├── Compatibility Engine
 ├── Inheritance Engine
 ├── Mutation Engine
 ├── Expression / Phenotype Resolver
 ├── Morphology Planning / Validation
 ├── Kinship Engine
 ├── Genome Codec + Version Migration
 ├── Probability Calculator
 └── Deterministic Test Suite

Genesis Hytale Adapter
 ├── NPC lifecycle / AI integration
 ├── Taming interaction
 ├── Breeding structures and events
 ├── Entity components / persistence
 ├── Models / attachments / rendering
 ├── UI and input
 ├── Permissions / commands
 ├── Multiplayer sync
 └── World/Server configuration

Genesis Content Packs
 ├── Base rig assets and modules
 ├── Species / hybrid definitions
 ├── Textures / animation profiles
 ├── Items / structures / sounds
 ├── Abilities / combat profiles
 └── Localization
```

**Обязательный архитектурный инвариант (ADR-001):** эти уровни не зависят от сторонних модов. `Genesis Public API` — публичная версионируемая граница, а совместимость с чужими системами обеспечивают только необязательные отдельные адаптеры. Genesis не должен автоматически изменять всех NPC; первичный контроль над Genesis-сущностью принадлежит одному контроллеру (раздел 24).

Конкретные классы, пакеты и доступность Hytale API необходимо **верифицировать на актуальной версии сервера** до реализации адаптера. Не считать предположения о динамической сборке модели готовой возможностью движка.

### 18.2. Предлагаемые сервисы

| Сервис | Ответственность |
|---|---|
| `GenomeEngine` | Аллели, наследование, de novo мутации |
| `CompatibilityService` | Группа, rig, допуски, ограничения пары |
| `PhenotypeResolver` | Проявление генов и значения характеристик |
| `MorphologyResolver` | Выбор совместимых визуальных модулей |
| `BreedingService` | Попытка, RNG, готовность, транзакция результата |
| `SparkRepository` | Хранение Искр без NPC |
| `CreatureRegistry` | UUID, экземпляры, владельцы, жизненные стадии |
| `LineageService` | Граф предков, происхождение, коэффициент родства |
| `DiscoveryRegistry` | Первые воплощения, авторы, породы |
| `GenesisCodeCodec` | Детерминированная сериализация/валидация |
| `CompanionAI` | Команды, сопровождение, боевые роли |
| `BreedingUI` | Интерфейсы селекции и анализа |

### 18.3. Пример сохранения генома

```json
{
  "schemaVersion": 1,
  "rulesetId": "genesis-rules-1",
  "familyId": "canids",
  "hybridArchetypeId": "wolf_fox",
  "genome": {
    "FRAME": ["normal", "large"],
    "HEAD": ["wolf", "fox"],
    "LIMBS": ["normal", "runner"],
    "APPENDAGE": ["wolf_tail", "bushy_tail"],
    "PIGMENT": ["dark", "shadow"],
    "COVER": ["dense_fur", "short_fur"],
    "MUSCLE": ["strong", "normal"],
    "STAMINA": ["normal", "high"],
    "METABOLISM": ["normal", "fast"],
    "SENSE": ["keen_smell", "night_vision"],
    "TEMPER": ["loyal", "cautious"],
    "ARCANA": ["dormant", "shadow_affinity"]
  },
  "cosmeticVariantSeed": "0000000000000042"

```

Все используемые пары аллелей должны иметь описание экспрессии. Происхождение, `creatureId`, текущий возраст, owner ID и обучение хранятся **в другом документе/компоненте**.

### 18.4. Событие разведения

```json
{
  "breedingEventId": "uuid",
  "parentAId": "uuid-a",
  "parentBId": "uuid-b",
  "initiatorPlayerId": "player-uuid",
  "generationSeed": "rng-seed",
  "rngVersion": "genesis-prng-v1",
  "rulesetId": "genesis-rules-1",
  "resultSparkId": "uuid-spark",
  "status": "succeeded"
}
```

Событие необходимо сохранять атомарно с расходованием попытки и созданием Искры. Повтор запроса с тем же `breedingEventId` должен возвращать тот же результат, а не создавать дополнительную Искру.

### 18.5. API ядра (контракт, не готовый мод)

```java
public interface BreedingEngine {
    BreedingResult breed(
        CreatureGenome parentA,
        CreatureGenome parentB,
        BreedingContext context,
        RandomGenerator random
    );
}

public interface PhenotypeResolver {
    Phenotype resolve(CreatureGenome genome, GeneticRules rules);
}

public interface MorphologyResolver {
    Morphology resolve(CreatureGenome genome, MorphologyRegistry registry);
}
```

RNG инжектируется извне, версии алгоритмов фиксируются. Генетическое ядро тестируется без поднятого игрового сервера.

### 18.6. Сохранения и надёжность

- Сервер — единственный источник истины для рождения, генома, Искр и открытий.
- Данные имеют `schemaVersion` и миграции.
- Генотип и результат мутации фиксируются до ответа UI.
- Новые UUID создаются при каждом воплощении/спавне.
- Данные владельца и вьючные инвентари сохраняются при выгрузке, смерти, переносе и перезапуске.
- События разведения и открытия идемпотентны.
- Питомцы вне активной зоны не требуют полноценного боевого AI-тика.
- База и UI защищены от дублирования Искр при лаге/обрыве связи.

- Собственные компоненты Genesis не добавляются всем ванильным NPC автоматически; один primary controller управляет жизненным циклом Genesis-существа.
- Genesis не удаляет сторонние ECS-компоненты и не перезаписывает чужие модификаторы атрибутов.
- Неизвестные данные отключённого расширения сохраняются без потерь, а зависимые операции блокируются до разрешения определения.
- Все контракты владения и интеграций определяются ADR-001 (раздел 24).

## 20. Симуляции, тестирование и критерии качества

### 20.1. Тесты наследования

| Сценарий | Ожидание |
|---|---|
| `A/a × A/a` | 25% `A/A`, 50% `A/a`, 25% `a/a` |
| `A/A × a/a` | 100% `A/a` |
| Два независимых рецессивных гена | 6,25% проявления обоих |
| Разные группы | Отказ до расхода попытки |
| Новая мутация | В среднем около 8% |
| Один генотип и ruleset | Одинаковый фенотип |
| Один Genesis Code | Одинаковый геном и косметика |
| Создание из одного кода дважды | Разные `creatureId` |
| Родные брат и сестра от неродственных основателей | `F_child = 0,25` |
| `inbreeding.mode=off` | Нет дополнительной ослабленности |
| Любой разрешённый генотип | Нет неразрешимого rig/модуля |
| Повтор сетевого запроса | Нет дублирования Искры |
| Два одновременных первых открытия | Один победитель уникального ключа |

Большие частотные тесты — 100 000+ синтетических потомков на фиксированных вариантах пар с допусками, основанными на статистическом разбросе.

### 20.1.1. Интеграционные тесты совместимости

Для MVP обязательны проверка запуска без внешних модов, отсутствие массового перехвата ванильных NPC, сохранность собственных геномов при удалении адаптера, отсутствие потери чужих баффов и дублирования событий, безопасный отказ для Genesis Code с неизвестными расширениями. Полная матрица и критерии приёмки — в ADR-001, п. 24.9.

### 20.2. Плейтесты

- Сколько времени игроку требуется до первого питомца и первого гибрида?
- Возвращается ли игрок к ручной мини-игре добровольно после автоматизации?
- Понимает ли разницу между совместимостью пары и вероятностью желаемого генотипа?
- Сколько Искр рассеивается, сколько воплощается и почему?
- Создаёт ли оптимальная стратегия одно доминирующее животное во всех режимах?
- Насколько часто игроки прекращают игру из-за невезения/переизбытка рутины?
- Удобен ли интерфейс генов при десятках производителей?
- Стабильны ли модули анатомии на сервере при множестве NPC?

### 20.3. Анализ баланса

Симулятор генерирует партии генотипов, затем сравнивает боевую эффективность, путешествия по биомам, скорость перевозки ресурсов, выпуск хозяйственных материалов с учётом пищи и энергии. Нужен **Парето-анализ**: не должно существовать одного дешёвого и доступного генотипа, который превосходит остальные по всем значимым ролям.

### 20.4. Проверка UX и доступности

Тестировать управление клавиатурой, действия без таймера, ясность обратной связи, отсутствие цветового кодирования как единственного сигнала, подтверждения рассеивания редких Искр и читаемость скрытых признаков.

## 21. MVP, этапы реализации и риски

### 21.1. Минимальный играбельный MVP

**Содержание:** одна группа (Клыкастые), два исходных вида (волк, лисица), один гибридный архетип, 12 базовых локусов с небольшим набором аллелей, несколько полезных/вредных мутаций, приручение, короткая мини-игра разведения, Искры, Колыбель, взросление, базовый спутник, Genesis Code, сохранение и серверная настройка инбридинга.

**Обязательная совместимость MVP (ADR-001):** автономный запуск; локальная принадлежность NPC; отсутствие глобального перехвата и записи в чужие компоненты; идемпотентное разведение; сохранность нераспознанных данных расширений. Полный API сторонних видов и отдельные адаптеры не требуются для MVP.

**Не включать в ранний MVP:** четыре полноценные группы, все хозяйственные линии, уникальные магические анимации, рынок, межгрупповые гибриды и глобальные Хроники.

### 21.2. Порядок работ

| Этап | Действия | Критерий готовности |
|---|---|---|
| **0. Технический spike** | Проверить сборку головы/хвоста/текстуры и синхронизацию NPC в Hytale | Рабочий визуальный прототип или подтверждённый fallback |
| **1. Genesis Core** | Наследование, мутации, локусы, выражение, код, тесты | Детерминированные расчёты и тестовые векторы |
| **2. Игровой вертикальный срез** | Волк/лисица, приручение, вольер, Искра, воплощение | Полный цикл от дикого животного до гибрида |
| **3. Селекция** | Лаборатория, родословная, породы, инбридинг, рекомендации | Игрок может целенаправленно вывести комбинацию |
| **4. Роли** | Маунты, вьючные, хозяйство, разведка, способности | Роли полезны и отличаются по экономике |
| **5. Социальный слой** | Хроники, авторство, обмены, внешний калькулятор | История открытий проверяема и переносима при заданных правилах |

### 21.3. Ключевые риски

| Риск | Последствие | Митигирование |
|---|---|---|
| Ограничения Hytale в динамической анатомии | Невозможно собрать произвольный гибрид | Spike на старте; целые базовые модели + attachments |
| Слишком большая комбинаторика | Недостаточно моделей, нестыковки | Family rigs, таблицы допустимых модулей, авторская валидация |
| Гринд ради редких генов | Игрок бросает мод | Искры, прогнозы, автоматизация, дикие носители |
| Эксплойт массового разведения | Лаги, неконтролируемые ресурсы | Серверные лимиты, cooldown, атомарность, стоимость |
| Необъяснимые плохие результаты | Раздражение | Отображение известных рисков, журнал, анализ |
| Несовместимые версии кода | Потеря идентичности существ | Версионирование ruleset, миграции, ясный отказ |
| Подмена первооткрытий | Недоверие к Хроникам | Серверные события, запрет наград админ-спавну |
| Универсально сильная комбинация | Исчезновение выбора видов | Стоимости физиологии и тесты по нескольким сценариям |
| Конфликт с другим модом на том же NPC | Конкурирующие ИИ, модель, инвентарь, сохранения | Явное владение, запрет автоматического перехвата, проверка известных конфликтов (ADR-001) |
| Удалено внешнее расширение с генами | Потеря данных/невоспроизводимый Genesis Code | Opaque-хранение unknown payload и безопасный отказ для зависимых операций |

## 22. Пример полного игрового сценария

**Цель игрока:** вывести быстрого ночного волколиса как боевого компаньона.

1. **Поиск.** Игрок находит лесного волка, наблюдает за его территориальным поведением, узнаёт предпочитаемый корм и приручает через мини-игру доверия.
2. **Второй производитель.** В другой области находит лисицу со скрытым геном теневого окраса, изучает её в лаборатории.
3. **Вольер.** Назначает пару, подбирает условия, проходит три раунда «Гармонии». Удачный раунд повышает шанс успешной попытки, но не «выбирает» теневой ген.
4. **Искра.** Появляется генетический образец. Анализ показывает интересный окрас, но слабые суставы. Игрок рассеивает Искру; физическое животное не возникало.
5. **Новая попытка.** После восстановления пары получает Искру со скоростью и нужным носительством, сохраняет её, чтобы иметь материал для следующего поколения.
6. **Закрепление.** Со временем подбирает производителей с более выгодными сочетаниями аллелей и повышает долю нужных потомков согласно обычным законам наследования.
7. **Воплощение.** Создаёт детёныша из лучшей Искры, наблюдает за развитием внешности, обучает командам и назначает роль «Охотник».
8. **Экспедиция.** Получает пользу от ночного восприятия, но учитывает низкую броню и расход энергии.
9. **Наследие.** Сохраняет Genesis Code, при выполнении условий регистрирует породу, а при первом воплощении редкой формы на сервере — запись в Хрониках.

**Результат:** цикл сочетает исследование мира, поведенческую мини-игру, вероятностную селекцию, осознанный выбор и долгосрочную коллекционную цель без необходимости держать десятки лишних NPC.

## 23. Реестр решений и открытых вопросов

### 23.1. Зафиксировано концепцией

- Название: **Genesis**.
- Фэнтезийные гибриды внутри совместимых групп.
- Умеренная генетика (12 диплоидных независимых локусов для MVP).
- Модульная морфология с ограниченными и валидируемыми rig.
- Отрицательные мутации и осмысленные физиологические компромиссы.
- Приручение через наблюдение и взаимодействие.
- Разведение через вольер и необязательную в дальнейшем мини-игру.
- Искры жизни вместо обязательного рождения каждого генома.
- Родство с настройками `off / soft / strict`.
- Genesis Code, отдельные UUID экземпляров и детерминированность по версии ruleset.
- История открытий и право первооткрывателя в рамках сервера.
- Равноправные сценарии боя, путешествий, хозяйства и коллекционирования.
- Genesis полностью автономен, без обязательных зависимостей от других модов (ADR-001).
- Для NPC применяется явный primary controller; нет автоматического перехвата чужих существ или глобального изменения всех животных.
- Внешние расширения допускаются только через namespaced и версионируемый публичный API либо отдельные необязательные адаптеры.
- При конфликте приоритет — отказ от конкретной операции без потери чужих данных; неизвестные гены не удаляются.

### 23.2. Начальные параметры, **не утверждённый баланс**

- 90%/70%/0% базовая совместимость.
- 8% новых мутаций (4% косметических; 2,5% физиологических; 1% поведенческих; 0,5% аномальных).
- 10 минут восстановления между попытками.
- 8/32 мест хранения Искр.
- 25% возврат обычных расходников при рассеивании.
- Два спутника и один активный маунт.
- Условия регистрации породы 3 поколения / 8 оценённых / 75% проявления.
- Числа характеристик и ограничений ролей из раздела 11.

### 23.3. Требует решения/проверки

1. **Hytale model spike:** какие части NPC реально можно динамически заменять и как это взаимодействует с анимациями/коллизиями?
2. **Искры:** физический предмет, блоковый контейнер, серверный реестр или гибридная схема? Как предотвращать дюпы при переносе?
3. **Рецепты вольеров:** сложность и стоимость для разных этапов прогрессии.
4. **Точность и длительность мини-игр:** сколько действий оптимально, когда открывать авто-режим?
5. **Конкретный набор аллелей:** таблицы парной экспрессии для всех 12 локусов каждого семейства.
6. **Сочетание мутаций:** политика допуска новых аллелей и совместимость арканных эффектов.
7. **Родословные:** хранить полный граф или архивировать старые поколения, как учитывать неизвестных предков.
8. **Питомцы после смерти:** возрождение, травмы или окончательная потеря; нужна серверная настройка.
9. **Рынок/обмен:** следует ли скрывать полные коды генетически ценных животных?
10. **Хроники:** точное определение «редкой формы», правила смены названий и право авторства при передаче Искры.
11. **Детерминированность разных серверов:** единый набор правил/моделей или режим совместимости с явными предупреждениями.
12. **Монетизация/распространение (в будущем):** лицензия, требования к зависимостям и ассетам Hytale.
13. **Интеграционный spike:** как определять external primary controller, реализовать source-aware модификаторы, оценить границы Hytale ECS и жизненного цикла событий?
14. **Публичный API:** какой минимальный набор контрактов стабилизировать в v1, а что оставить экспериментальным?
15. **Трансфер NPC между модами:** протокол handshake и миграции не входит в MVP; реализовать только при наличии обоюдного API.

## 24. ADR-001 — Автономность Genesis и совместимость с другими модами

> **Статус:** принято · **Дата:** 15 октября 2026 · **Область:** архитектура, данные, NPC, публичные интеграции  
> **Приоритет:** обязательные принципы для MVP; расширенный сторонний API можно выпускать поэтапно.

### 24.1. Контекст и решение

На одном сервере могут работать несколько модов, добавляющих приручение, питомцев, характеристики, модели или собственные виды. Если каждый мод безусловно перехватывает одних и тех же NPC, возникают конфликты ИИ, сохранений, анимаций и игрового владения.

**Принятое решение:** Genesis полностью функционирует **без обязательных зависимостей от других модов**. Все обязательные механики (приручение, разведение, генетика, мутации, модульная морфология, Искры жизни, команды, хранение, Genesis Code) реализуются внутри Genesis и через Hytale API. Никакой код стороннего мода не является обязательным условием запуска.

Различаются две цели:

- **Сосуществование (compatibility):** Genesis не присваивает чужих NPC, не портит чужое состояние и по возможности не мешает установленным модам.
- **Интеграция (interoperability):** мод, явно использующий Genesis API или установленный отдельный адаптер, может регистрировать виды, генетику, способности и согласованные точки взаимодействия.

Первая цель обязательна в MVP, вторая — архитектурный контракт с поэтапной реализацией. **Абсолютная бесконфликтность с произвольными модами не гарантируется:** чужой мод может без согласования переопределять глобальные NPC, AI или модельные компоненты.

### 24.2. Зависимости и границы модулей

```text
Genesis Core (pure Java; no Hytale or third-party mod dependency)
    ↑
Genesis Public API (versioned contracts, immutable DTOs, extension points)
    ↑
Genesis Hytale / Gameplay (server authority, persistence, UI, NPC control)

Third-party compatibility adapter (optional and separately deployed)
    ├── depends on Genesis Public API
    └── depends on the external mod API, if required
```

Схема отражает логические границы, а не обязательное разбиение на JAR: Genesis может распространяться единым модом. Публичный API не должен предоставлять обходной доступ к внутренним mutable-структурам. Основной manifest Genesis **не содержит** ссылок на известные сторонние моды; зависимости декларирует лишь отдельный адаптер. Отсутствие или удаление адаптера не мешает запуску Genesis.

**Правило зависимостей:** `genesis-core` не импортирует классы Hytale и внешних модов; `genesis-hytale` не импортирует классы Animal Husbandry / Tamework / иных модов. Интеграционный адаптер зависит от Genesis, а не наоборот.

### 24.3. Authority: владение сущностью и подсистемами

`GenesisCreatureComponent` — явный маркер существа под управлением Genesis. Он добавляется **только** при создании существа Genesis или после успешно подтверждённого принятия управления. Нельзя автоматически добавлять его всем ванильным животным при загрузке мира или сканировании чанков.

Предлагаемые компоненты (имена концептуальные, точный ECS API проверяется в Hytale):

```text
GenesisCreatureComponent       — identity + schema version + primary controller
GenesisGenomeComponent         — наследственный геном и ruleset
GenesisOwnershipComponent      — владелец, контроль доступа, provenance
GenesisMorphologyComponent     — rig, модули, варианты внешности
GenesisCompanionComponent      — команды, роль, обученность
GenesisExtensionDataComponent  — сохранённые данные разрешённых расширений
```

**Primary controller** для NPC только один. Он отвечает за приручение, управление поведением, размножение и целостность хранимого состояния Genesis-существа. Дополнительные модификаторы (внешний бафф, косметический overlay) могут сосуществовать с основным контроллером, если их эффект согласован через поддерживаемый интерфейс.

| Ситуация | Поведение Genesis |
|---|---|
| Дикий ванильный NPC без известного владельца | Не изменять автоматически; начать приручение только при явном действии игрока Genesis |
| NPC с `GenesisCreatureComponent` | Управление Genesis; чужие расширения только через разрешённые контракты |
| NPC под известным управлением другого мода | Не перехватывать; отклонить конфликтующую операцию |
| NPC чужого добавленного вида | Не импортировать автоматически; нужна регистрация вида или адаптер |
| Происхождение/владение невозможно достоверно установить | Не делать безусловных предположений; при риске конфликта отказать или запросить явно разрешённый сценарий |
| Передача управления | Только явный handshake адаптеров, с правами, проверками и атомарной сменой владельца |

`playerOwnerId` (игровой хозяин) и `primaryControllerId` (мод/подсистема, управляющая NPC) — **разные понятия**. Считывание чужих метаданных не делает Genesis их владельцем. Универсального способа распознать управление любого неизвестного мода нет; проверка чужой принадлежности возможна только по поддерживаемым сигналам/API.

### 24.4. Правила записи и разрешения конфликтов

| Подсистема | Источник истины и границы изменений |
|---|---|
| Геном / наследование | Genesis Core и `BreedingService`; сторонние расширения регистрируют определения до фиксации ruleset |
| Размножение | Только назначенный controller создаёт событие разведения и Искру; повторная обработка идемпотентна |
| ИИ / навигация / команды | Один primary controller поведения; другая система не назначает конкурентный AI-loop |
| Основная модель, rig, хитбокс | Один контроллер основной анатомии; внешние overlays — лишь в допустимых слотах |
| Атрибуты / эффекты | Независимые модификаторы с namespaced source ID, без постоянной перезаписи общего значения |
| Инвентарь и предметы | Единственный авторитетный контейнер, доступ через разрешённые операции |
| Persistence | Genesis обновляет лишь свои данные; чужие компоненты не стираются и не мигрируются |
| Владение игрока | Только сервис Genesis Ownership; никакой прямой записи сторонними обработчиками |

Для атрибутов предпочтителен учёт вклада по источнику, например `genesis:genetic_strength` и `othermod:equipment_bonus`. Повторная загрузка, повторное событие и снятие эффекта должны быть идемпотентными; при отсутствии готового механизма атрибутов в Hytale нужен собственный reconciler или отказ от неподдерживаемой интеграции. Запрещено каждый тик выставлять абсолютное `strength=70`, затирая внешний бафф.

Передача существа внешней системе **не входит в MVP**. Если её добавлять, обязателен протокол: проверить обе стороны и разрешения → заморозить изменяемые действия → создать переносимый snapshot → подтвердить принятие целевой системой → атомарно сменить controller → освободить исходные ресурсы; при любой ошибке — откат без дублирования экземпляров или инвентаря.

### 24.5. Публичный API расширений

Внутренние пакеты не считаются публичным API. Отдельный `GenesisApi` предоставляет read-only доступ к геномам и сущностям и строго ограниченные операции через сервисы. Все ID регистрируемого контента имеют namespace вида `genesis:wolf`, `examplemod:dragon`; зарегистрированные ID нельзя перезаписывать без явного разрешения и версии миграции.

| Контракт | Возможность стороннего разработчика |
|---|---|
| `CreatureProvider` | Добавить определение совместимого вида/архетипа |
| `GeneticsExtension` | Зарегистрировать аллели, локусы, правила экспрессии и миграции |
| `MorphologyProvider` | Добавить разрешённые rig-модули и связанные ассеты |
| `AbilityProvider` | Добавить способности с заявленными требованиями, стоимостью и cooldown |
| `CompatibilityPolicy` | Проверить/запретить конкретную операцию в разрешённой точке |
| `GenesisEvents` | Подписаться на документированные события жизненного цикла |

Контракты — **проект API**, не утверждение о наличии классов в Hytale:

```java
public interface GenesisApi {
    CreatureViewService creatures();
    GeneticDefinitionRegistry genetics();
    MorphologyDefinitionRegistry morphology();
    BreedingOperations breeding();
    GenesisEvents events();
}

public interface CreatureProvider {
    String namespace();
    Collection<CreatureDefinition> definitions();
}
```

Доступ к `GenesisCreature` извне — через immutable snapshots; изменение генома — только в заранее разрешённом workflow создания/мутации, с валидацией и версионированием. Критически важные определения фиксируются после загрузки контента и до начала игровых расчётов (**registry freeze**). Горячая замена генетических правил без миграции существ запрещена.

Стабильный API должен быть версионирован отдельно от внутренней реализации. Несовместимые изменения требуют новой major-версии API, миграций и явно задокументированной политики поддержки.

### 24.6. События и согласование операций

**До фиксации (`Before*`)** допускаются ограниченные проверки и отмена операции, но не произвольная мутация генома. **После фиксации (`After*`)** передаются неизменяемые данные о совершившемся результате.

Примеры: `BeforeTamingEvent`, `BeforeBreedingEvent`, `BreedingCompletedEvent`, `LifeSparkCreatedEvent`, `CreatureManifestedEvent`, `CreatureReleasedEvent`, `MutationDiscoveredEvent`, `SpeciesDiscoveredEvent`.

Порядок для разведения:

```text
request → identify controller → permission & ownership checks
        → validate parents & compatibility → BeforeBreeding validators
        → reserve resources / enforce idempotency
        → compute + commit genome, event and Spark atomically
        → publish immutable post-commit events
```

Сторонние обработчики не должны получать ссылку на mutable-геном или изменять завершённую транзакцию. Ошибка/таймаут обязательного pre-validation шага означает безопасный отказ без расхода попытки. Сбой post-commit listener не откатывает рождение и не запускает повторную мутацию; надёжные подписчики должны использовать ID события, идемпотентность и, если требуется, outbox/retry. Подписки и вызовы адаптеров не должны блокировать серверный тик неопределённо долго.

### 24.7. Genesis Code, внешние данные и исчезающие расширения

В Genesis Code и серверном геноме допускаются **только** зарегистрированные namespaced-аллели и versioned extensions. Запись расширения содержит `extensionId`, `schemaVersion` и детерминированный сериализуемый payload. Канонический порядок и формат байтов должны быть задокументированы, иначе одинаковый геном не даст одинаковый код.

Если требуемое расширение отсутствует:

1. Не удалять и не подменять неизвестный ген или payload в сохранённых данных.
2. Сохранять исходные байты/метаданные для возможного восстановления после установки расширения.
3. Не допускать скрещивание, мутацию, импорт или спавн, для которых невозможно корректно разрешить обязательные определения.
4. По умолчанию `missingExtensions = reject` для воспроизведения; визуальный fallback допустим только для явно необязательной косметики, не изменяя геном.
5. Административные импорты не получают заслуг первооткрывателя (см. раздел 16).

Внешнее расширение не может использовать поле `genesis:*` без авторизации. Checksum в коде — контроль случайной порчи, **не** подпись доверенного сервера или доказательство происхождения.

### 24.8. Настройки и политика развёртывания

Основная конфигурация Genesis включает `compatibility` (см. раздел 19). По умолчанию действуют `respectExternalOwnership = true`, `allowAutomaticTakeover = false`, `allowExplicitTransfer = false`, `conflicts.policy = deny`, `genesisCode.missingExtensions = reject`.

Интеграционные адаптеры устанавливаются **отдельно**. Администратор может отключить расширения и интеграции, не отключая базовую игру Genesis. При отключении расширения уже сохранённые данные должны оставаться читаемыми как неразрешённые/opaque, пока администратор не выполнит явную миграцию.

Конфликт `deny` отклоняет конкретную операцию, **не отключает весь Genesis**. Действия логируются структурированно: `entityId`, `operation`, `otherController` (если известен), `reason`, `decision`; идентификаторы и личные сведения в логах должны минимизироваться.

### 24.9. Тесты и критерии приёмки ADR-001

| Сценарий | Обязательное ожидание |
|---|---|
| На сервере установлен только Genesis | Доступен весь базовый игровой цикл, нет ClassNotFound ошибок из-за внешних модов |
| Установлен другой мод приручения | Genesis не перехватывает известного чужого питомца |
| Ванильный NPC появился в мире | Genesis не меняет его автоматически без взаимодействия |
| Два мода пытаются управлять NPC | Для известных конфликтов отклоняется второй primary controller |
| Внешний источник добавляет бонус | Собственный модификатор Genesis не стирает чужой и не дублируется после reload |
| Удалён интеграционный адаптер | Genesis запускается; его данные и свои питомцы не повреждены |
| Удалено расширение с новым геном | Payload сохраняется, зависимые операции отклоняются с понятной ошибкой |
| Импорт кода с неизвестным `examplemod:*` | Нет частичного спавна и молчаливого fallback генов |
| Повтор запроса разведения | Одна транзакция, одна Искра, один набор событий результата |
| Ошибка внешнего listener | Фиксированное потомство не теряется и не генерируется повторно |
| Два игрока получают первое открытие | Право первооткрытия присваивается атомарно одному событию |
| Отключены все интеграции | Приручение, генетика, спавн по коду и сохранение работают |

**Критерий завершения MVP:** Genesis работает автономно; не производит глобальной модификации всех NPC; есть проверяемая принадлежность собственных питомцев; операции разведения идемпотентны; хранение данных внешних расширений не разрушает исходный геном. Дополнительный рынок внешних видов и адаптеры могут появиться позже.

### 24.10. Риски и вопросы для технического spike

- Какие сигналы Hytale и сторонних модов доступны, чтобы установить primary controller? Если надёжного сигнала нет, используется консервативная политика, без обещания детектировать все моды.
- Позволяет ли серверный API атрибуты с модификаторами по источнику? Если нет — нужен адаптер/собственный слой согласования.
- Как безопасно согласовать event lifecycle, транзакции и сохранение ECS-компонентов без дюпов?
- Можно ли динамически прикреплять косметические модули без перезаписи чужой модели/анимации?
- Какая версия API расширений нужна на первый публичный релиз и где проходит граница стабильности?

**Итог ADR-001:** Genesis не заимствует обязательную логику или runtime-зависимости у сторонних модов; он предлагает **контролируемые, необязательные** точки расширения и безопасные правила обработки конфликтов. Дополнительные механизмы интеграции не должны ставить под угрозу самостоятельность Genesis.

## Итог

Genesis строится вокруг четырёх последовательных удовольствий игрока:

1. **Понять и приручить** интересное существо.
2. **Спланировать и получить** новое сочетание наследственных признаков.
3. **Выбрать, вырастить и применить** действительно ценное животное.
4. **Оставить след** в истории пород и открытий своего сервера.

Система Искр жизни снимает основную проблему случайной массовой селекции, Genesis Code даёт воспроизводимость и основу для веб-инструментов, модульная анатомия делает наследственность видимой, а серверные настройки позволяют подобрать сложность для одиночной игры и публичных серверов.

**Первый технический приоритет — проверить возможности модульной анатомии в актуальном Hytale; первый игровой приоритет — вертикальный срез «волк + лисица → мини-игра → Искра → воплощённый гибрид».**
